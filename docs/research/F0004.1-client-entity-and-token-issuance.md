## §2 — Execution Path

**Existing analogous flow — `POST /auth/login` (Admin identity, for reference):**

1. `AuthController.Login(LoginCommand command)` (`back-end/ONG.API/Controllers/AuthController.cs:18`) — receives model-bound `LoginCommand` (`Username`/`Password`, both `[Required]`, `back-end/ONG.Application/UseCases/Auth/Login/LoginCommand.cs:5-12`).
2. → `LoginHandler.Handle(command)` (`back-end/ONG.Application/UseCases/Auth/Login/LoginHandler.cs:29-53`), constructor-injected with `IAdminRepository`, `ITokenGenerator`, `IPasswordHasher<Admin>` (17-27).
   - `_repository.GetByUsername(command.Username)` (31) → `AdminRepository.GetByUsername` (`back-end/ONG.Infrastructure/Repositories/AdminRepository.cs:8-21`, wraps `_context.Admins.FirstOrDefault(a => a.Username == username)`).
   - If not found: runs a dummy `HashPassword` call against a static `DummyAdminForTimingNormalization` field for timing-attack normalization (comment lines 10-14, 35-41), returns `null`.
   - If found: `_passwordHasher.VerifyHashedPassword(admin, admin.PasswordHash, command.Password)` (45); on `Failed`, returns `null` (46-49).
   - On success: `_tokenGenerator.GenerateToken(admin)` (51) → `JwtTokenGenerator.GenerateToken` (see §1) → `LoginResult(token)` returned (52).
3. → Controller: `null` result → `Unauthorized(new { message = "Invalid username or password." })`; non-null → `Ok(result)` (serializes `{ "token": "<jwt>" }`, `LoginResult.cs` single `string Token` property).

**Existing seeding flow (startup, for reference):** `Program.cs:97-112` — `JwtTokenGenerator.ValidateConfiguration` → `dbContext.Database.Migrate()` (relational-only) → `AdminSeeder.Seed(dbContext, builder.Configuration)`, which itself calls `AdminSeeder.ValidateConfiguration` before any DB read (`AdminSeeder.cs:15`).

No `Client` entity, `oauth` route, or client-token code exists anywhere in the repo today — confirmed via repository-wide case-insensitive search for `oauth` (zero source-code hits) and for `Client` as a domain concept (only unrelated matches like `HttpClient`/`WebApplicationFactory`).

## §3 — Existing Patterns (reuse)

> Facts about what exists — not a recommendation to use them (that is design).

- `Admin` entity shape (`Admin.cs:5-33`) — `Guid Id`, string fields with private setters and `= string.Empty` defaults, constructor stamping `CreatedAt`/`UpdatedAt`, named mutation methods (`Rename`, `RotatePassword`) instead of public setters.
- `AdminSeeder` static seed-or-reconcile pattern (`AdminSeeder.cs:13-53`) — idempotent: create if absent, reconcile+`SaveChanges` only if drifted, no-op otherwise. Locally-constructed `PasswordHasher<T>` from config-bound `PasswordHasherOptions`, independent of the DI-registered instance.
- `ValidateConfiguration` fail-fast pattern, present twice (`AdminSeeder.cs:55-91`, `JwtTokenGenerator.cs:48-84`) — both accumulate all missing/invalid keys into one list, throw a single `InvalidOperationException` naming every failure, called from `Program.cs` before any `DbContext` use.
- `IAdminRepository`/`AdminRepository` pair (`back-end/ONG.Application/Repositories/IAdminRepository.cs:5-8`, `back-end/ONG.Infrastructure/Repositories/AdminRepository.cs:8-21`) — minimal single-method read repository (`GetByUsername`), constructor-injects `ONGDbContext`.
- `IAnimalRepository`/`AnimalRepository` pair (`back-end/ONG.Application/Repositories/IAnimalRepository.cs:5-12`, `back-end/ONG.Infrastructure/Repositories/AnimalRepository.cs`) — richer repository with `Add`, explicit `SaveChanges()` (24-27, thin passthrough to `_context.SaveChanges()`), `GetAll(filter)`, `GetById(id)`. Handler calls `Add` then `SaveChanges` as two explicit calls (no implicit unit-of-work).
- Command+Handler folder convention: one folder per use case under `UseCases/<Aggregate>/<UseCase>/` (e.g. `UseCases/Auth/Login/LoginCommand.cs` + `LoginHandler.cs`), handler constructor-injects only the interfaces it needs, registered individually via `AddScoped<XHandler>()` in `Program.cs` (no interface for handlers themselves — called directly from controllers, no mediator).
- `ITokenGenerator`/`JwtTokenGenerator` (`back-end/ONG.Application/Security/ITokenGenerator.cs:5-8`, `JwtTokenGenerator.cs`) — currently `Admin`-specific (`GenerateToken(Admin admin)`), registered `AddScoped<ITokenGenerator, JwtTokenGenerator>()` (`Program.cs:71`).
- `AuthController` bare-route convention (`AuthController.cs:6-8`) — `[Route("auth")]`, no `api/` prefix, unlike `AnimalController`'s `[Route("api/animals")]` (`back-end/ONG.API/Controllers/AnimalController.cs:12`). Explicit `null`-check → `Unauthorized(...)` pattern (22-25) rather than letting a failure fall through uncaught.
- `Configure<PasswordHasherOptions>(...)` + `AddScoped<IPasswordHasher<Admin>, PasswordHasher<Admin>>()` (`Program.cs:90-92`) — the only `IOptions<T>`-pattern usage in the codebase; `PasswordHasher<T>` is generic over the entity type (`PasswordHasher<Admin>`), meaning a `PasswordHasher<Client>` would be a distinct DI registration.
- Migration precedent for a new identity table (`AddAdminTable.cs`, see §1) — `CreateTable` + separate `CreateIndex(..., unique: true)` calls, `Guid`→`uuid`, `string`→`text`, `DateTime`→`timestamp with time zone`.
- Secrets flow-through pattern (`docs/CLAUDE.md` "Secrets & Deployment Configuration" table; `back-end/.env.example:19-26`; `back-end/docker-compose.yml:30-32`) — `.env`(local)/User Secrets(host-run)/GitHub Actions secrets(CI)/Render env vars(prod), each mapped via ASP.NET Core's double-underscore convention (e.g. `AdminSeed__Password`), each required key fail-fast-validated at startup.
- E2E test factory pattern: `LoginApiFactory` (`back-end/ONG.Tests/Api/LoginApiFactory.cs:14-52`) extends `WebApplicationFactory<Program>`, overrides `ConfigureWebHost` to inject in-memory config and swap `DbContextOptions<ONGDbContext>` to the InMemory provider (removing both `DbContextOptions<ONGDbContext>` and `IDbContextOptionsConfiguration<ONGDbContext>` descriptors, lines 44-48, with an explanatory comment for why both removals are needed).
- Integration-trait Postgres test pattern: `ONGDbContextTests.SavingSecondAdminWithDuplicateUsername_Throws` (`back-end/ONG.Tests/Infrastructure/ONGDbContextTests.cs:90-113`) — `[Trait("Category","Integration")]` (14), reads real connection string from User Secrets by `UserSecretsId` (20-39), probes Postgres reachability with an actionable failure message (45-66), asserts `DbUpdateException` on a duplicate unique-indexed value.

## §5 — Observed Conventions

- **Naming:** PascalCase properties throughout except the pre-existing, flagged `CreateAnimalCommand.approximateAge` defect (`CLAUDE.md`, do not copy). Entities use singular names (`Admin`, `Animal`); DbSets/tables use plural (`Admins`, `Animals`).
- **Layering / structure:** Controllers thin, call one handler once (`AuthController.cs:20`, `AnimalController.Create`). Handlers constructor-injected with interfaces only, no direct `Infrastructure` references (`LoginHandler`, `CreateAnimalHandler`). Repository interface in `ONG.Application/Repositories/`, implementation in `ONG.Infrastructure/Repositories/`. No `AddApplication()`/`AddInfrastructure()` extension methods yet — all DI registration is inline in `Program.cs`.
- **Error handling:** Inconsistent across controllers — `AuthController` explicitly checks for `null`/failure and returns `Unauthorized(...)` (22-25); `AnimalController.Create`/`List` (per `CLAUDE.md`) do not handle not-found/invalid-input explicitly and let it fall through. `AnimalController.GetById`/`Update` do have explicit `if (animal is null) return NotFound();` checks (per Explore agent report, not directly re-verified this session). `ExceptionHandlingMiddleware` exists in the pipeline (`Program.cs:123`) but its exact catch scope wasn't re-verified directly in this research pass (reported by Explore agent as catching only `ArgumentException`→400 and generic `Exception`→500; not independently confirmed).
- **Tests:** xUnit, `back-end/ONG.Tests/` organized by layer (`Api/`, `Application/`, `Domain/`, `Infrastructure/`). EF Core InMemory for unit/E2E tests (fresh `Guid`-named database per test for isolation), `WebApplicationFactory<Program>` for E2E HTTP tests (`Api/LoginEndpointTests.cs` + `Api/LoginApiFactory.cs`), one `[Trait("Category","Integration")]`-tagged test requiring real Postgres for unique-index enforcement (InMemory provider doesn't enforce secondary unique indexes). Run via `dotnet test ONG.slnx` (all) or `--filter "Category!=Integration"` (excludes the Postgres-dependent test).
- **Migrations:** `dotnet ef migrations add <Name>` naming convention `{yyyyMMddHHmmss}_{PascalCaseDescription}.cs` + paired `.Designer.cs`, applied automatically at startup via `dbContext.Database.Migrate()` (`Program.cs:106-109`, relational-only guard).

## §6 — Open Questions

> Collected, not answered — resolved in `design-slice`.

- Q1 — Should the new `POST /oauth/token` client-credential issuance reuse `ITokenGenerator`/`JwtTokenGenerator` (currently hard-typed to `GenerateToken(Admin admin)`) by generalizing/overloading it, or introduce a parallel, `Client`-specific token generator? The parent feature spec (line 165) explicitly defers this as a design-slice decision.
- Q2 — What `Jwt:*`-equivalent config keys does the client token use — the same `Jwt:Key`/`Jwt:Issuer` as the admin JWT (shared signing key/issuer), or a separate `Client`-specific key/issuer pair? NFR1 in the parent spec requires client tokens to be "short-lived (minutes, not hours)" — distinct from the existing `Jwt:ExpiryMinutes` default of 60 (`appsettings.json`), so at minimum a separate expiry value/config key is implied, but whether it shares the signing key/issuer is unresolved.
- Q3 — What exact shape does `ClientSeed`-equivalent configuration take (mirroring `AdminSeed:Username`/`AdminSeed:Password`)? Does it seed exactly one client, or must the seeding mechanism support multiple named clients (parent spec FR1 says "at least one active client per known application, e.g. `front-web`" — implying plural clients, unlike the single-admin-row precedent `AdminSeeder` follows via `OrderBy(...).FirstOrDefault()`).
- Q4 — Does `POST /oauth/token` sit under a new bare `[Route("oauth")]` controller (mirroring `AuthController`'s bare `[Route("auth")]`), or is it added to `AuthController` itself, or given the `api/` prefix like `AnimalController`? The parent spec's Public Contracts table (line 114) says "exact path confirmed in design."
- Q5 — What does the `Client` entity's constructor/mutation-method shape look like — does it follow `Admin`'s exact shape (constructor + `Rename`/`RotatePassword`-style behavior methods), and does `IsActive` toggle through a named method (e.g. `Deactivate()`) consistent with the rich-domain-entity convention, or is it a settable flag? (This slice's DoD only requires the entity+seed+issuance; `IsActive` enforcement/toggling itself is FR4, scoped to F0004.2, per the slice's own §1 Objective — but the entity shape including `IsActive` is this slice's concern since the column must exist now.)
- Q6 — Is `PasswordHasher<Client>` a second DI registration alongside the existing `PasswordHasher<Admin>` (`Program.cs:92`), and does client-secret verification follow the same `VerifyHashedPassword`/dummy-hash timing-normalization pattern used in `LoginHandler.cs:35-41` (parent spec's Security Considerations, line 104, requires the invalid-credential response not reveal whether `client_id` or `client_secret` was wrong)?
- Q7 — Does the response DTO for `POST /oauth/token` follow `LoginResult`'s single-`Token`-property shape, or does NFR1 (short expiry) imply the response should also echo an expiry/`expires_in` value (not present in the existing `LoginResult`)?

## §7 — Risks / Gotchas

- `AdminSeeder.Seed` assumes exactly one row via `OrderBy(a => a.CreatedAt).FirstOrDefault()` (`AdminSeeder.cs:21`) — this single-row assumption cannot be copied verbatim for `Client` if FR1 requires multiple seeded clients (e.g. `front-web` plus others); a naive copy-paste would silently only ever seed/reconcile one client row.
- `ITokenGenerator.GenerateToken(Admin admin)` (`back-end/ONG.Application/Security/ITokenGenerator.cs:5-8`) is hard-typed to `Admin` — it cannot be called with a `Client` without either an overload, a generic signature change, or a parallel interface; any change to this shared interface risks touching the existing, working `LoginHandler` flow.
- `Program.cs:97-112` runs `JwtTokenGenerator.ValidateConfiguration` → `Migrate()` → `AdminSeeder.Seed` inside one scope, in that literal order — a new `ClientSeeder`-equivalent must decide its position in this sequence (before/after `AdminSeeder.Seed`) and whether it needs its own `ValidateConfiguration` call before the `DbContext` is touched, mirroring the existing fail-fast precedent.
- `docs/features/F0004-client-credentials-auth.md` (parent spec, line 178) already marks F0004.1's status as "spec created / in research" and explicitly states F0004.1 does **not** enforce the new token on any route (that's F0004.2) — a design that accidentally wires global enforcement into this slice would blow the ~400-line diff budget and duplicate F0004.2's planned scope.
- `CLAUDE.md`'s Auth/multi-tenancy section (as of this repo's last update) states `[Authorize]` is applied "to `AnimalController.Create` only" — but direct/Explore verification found `[Authorize]` is now also on `AnimalController.Update` (added in commit `cf2011f`, `PUT /api/animals/{id}`, after that CLAUDE.md line was written). This is a **stale doc**, not a current-repo fact — relevant only in that CLAUDE.md itself may need a follow-up correction (out of this slice's scope) and that its assertions about auth coverage shouldn't be trusted uncritically for design decisions.
- The existing `Jwt:Key`/`Jwt:Issuer` config has no default `Jwt:Key` in `appsettings.json` (`ONG.API/appsettings.json:9-12` — only `Issuer`/`ExpiryMinutes` have defaults; `Key` is secret-only) — any new client-token signing key follows the same "no committed default" pattern per existing secrets convention, whether it reuses `Jwt:Key` or introduces a new key.
- `PasswordHasher<T>` is generic per-entity-type — reusing `PasswordHasherOptions`/`PasswordHasher:IterationCount`/`PasswordHasher:CompatibilityMode` config section for both `Admin` and `Client` is possible (same options can back multiple generic instantiations), but `AdminSeeder.cs:19`'s locally-constructed `new PasswordHasher<Admin>(...)` pattern would need an equivalent `new PasswordHasher<Client>(...)` construction if a `ClientSeeder` mirrors this exact static-seeder shape.
