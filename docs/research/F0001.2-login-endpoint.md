## §2 — Execution Path

Closest existing analogue (`POST /animals/{id}/adopt`), which the new `POST /auth/login` would mirror structurally:

1. `AnimalController.Adopt(Guid id)` (`AnimalController.cs:30`) — receives the route param, builds an `AdoptAnimalCommand` (L32–35).
2. → `AdoptAnimalHandler.Handle(command)` (`ONG.Application/UseCases/Animals/AdoptAnimal/AdoptAnimalHandler.cs`) — calls `_repository.GetById(command.AnimalId)`; if `null`, `throw new Exception("Animal not found.")` (L20, uncaught); else calls `animal.Adopt()` (domain behavior) then `_repository.SaveChanges()`.
3. → Controller returns `Ok(animal)` (`AnimalController.cs:39`). No explicit 404/400 path exists in this analogue — a not-found case currently surfaces as an unhandled 500, since no exception middleware/`UseExceptionHandler` exists anywhere in `ONG.API` (confirmed by repo-wide grep for `ExceptionHandler|ProblemDetails|try\s*\{`, zero matches).

For login specifically, the only existing credential-verification code path today is inside `AdminSeeder.Seed` (`AdminSeeder.cs:41`): `hasher.VerifyHashedPassword(admin, admin.PasswordHash, password)` against `Microsoft.AspNetCore.Identity.PasswordHasher<Admin>` — this is seed-time reconciliation, not a runtime login flow, and there is currently no controller, handler, command, or repository for `Admin` lookup by username.

## §3 — Existing Patterns (reuse)

- **Command+Handler pair** (`ONG.Application/UseCases/Animals/CreateAnimal/CreateAnimalCommand.cs` + `CreateAnimalHandler.cs`) — plain POCO Command, Handler constructor-injects a repository interface, synchronous `Handle()` returning a domain entity directly. No MediatR — Handlers are registered individually via `AddScoped<XHandler>()` in `Program.cs` and called directly from controllers.
- **Repository interface/implementation split** (`ONG.Application/Repositories/IAnimalRepository.cs` + `ONG.Infrastructure/Repositories/AnimalRepository.cs`) — interface in Application (`ONG.Application.Repositories` namespace), implementation in Infrastructure (`ONG.Infrastructure.Repositories` namespace), constructor-injects `ONGDbContext`, synchronous methods only.
- **`Microsoft.AspNetCore.Identity.PasswordHasher<Admin>`** (`AdminSeeder.cs:4,18`) — already the project's password-hashing mechanism, from the `Microsoft.Extensions.Identity.Core` NuGet package (`ONG.Infrastructure.csproj:16`, version `10.0.11`); exposes `HashPassword(user, password)` and `VerifyHashedPassword(user, hash, providedPassword)` returning `PasswordVerificationResult`.
- **Controller convention** (`AnimalController.cs`) — `[ApiController]` + class-level `[Route("{prefix}")]` (no leading slash, e.g. `"animals"`), action-level `[HttpPost]`/`[HttpPost("{sub}")]`, Command class taken directly as the action parameter (implicit JSON body binding).
- **`JsonStringEnumConverter`** (`Program.cs:12–17`) — registered globally for all controllers; relevant if any response/request DTO for login uses an enum.
- **Namespace/folder 1:1 mapping** — e.g. physical path `ONG.Application/UseCases/Animals/CreateAnimal/` → namespace `ONG.Application.UseCases.Animals.CreateAnimal`; a login use case following this convention would be folder `ONG.Application/UseCases/Auth/Login/` → namespace `ONG.Application.UseCases.Auth.Login`.
- **`docs/spec-driven-development.md:200-204`** explicitly names `Microsoft.AspNetCore.Mvc.Testing` (`WebApplicationFactory`) as the recommended approach for API-level tests "starting with `F0001.2`'s `POST /auth/login`" — not currently referenced anywhere in `ONG.Tests.csproj`.

## §5 — Observed Conventions

- Naming: PascalCase properties (one existing exception, `CreateAnimalCommand.approximateAge`, flagged in `CLAUDE.md` as a defect not to repeat). Test methods use `MethodUnderTest_Scenario_ExpectedOutcome` (e.g. `Seed_EmptyTable_InsertsAdminWithHashedNonPlaintextPassword`).
- Layering / structure: strict Command/Handler-per-use-case under `UseCases/<Aggregate>/<UseCase>/`; repository interface in Application, implementation in Infrastructure; controllers stay thin (build Command, call one Handler, return result) — though today they do so with **no validation or error branching at all**.
- Error handling: **no** custom exception types, **no** try/catch, **no** exception middleware anywhere in the current codebase. The one "not found" case (`AdoptAnimalHandler.cs:20`) throws a bare `System.Exception` and is left to become an unhandled 500. This is a documented gap in `CLAUDE.md` ("new endpoints should not repeat this gap; handle the not-found/invalid-input case explicitly").
- Tests: xUnit 2.9.2 + `Microsoft.EntityFrameworkCore.InMemory` 10.0.11 (`ONG.Tests.csproj`). No Moq/NSubstitute/FluentAssertions anywhere — plain `Assert.*`. No `Microsoft.AspNetCore.Mvc.Testing` package yet. `ONG.Tests.csproj` currently only references `ONG.Domain` and `ONG.Infrastructure` as `ProjectReference`s — **no reference to `ONG.Application` or `ONG.API`**, so no Command/Handler or Controller type is reachable from `ONG.Tests` without adding those references. Run via `dotnet test ONG.slnx` (all) or `dotnet test ONG.slnx --filter "Category!=Integration"` (skips the one Postgres-dependent test, the only `[Trait]` usage in the repo). CI (`.github/workflows/backend-docker.yml`) runs `dotnet build` and a Docker/Swagger smoke test only — it does **not** run `dotnet test`.

## §7 — Risks / Gotchas

- No authentication middleware exists at all (`Program.cs` has `UseAuthorization()` at L47 but no `UseAuthentication()`/`AddAuthentication(...)`) — whatever credential this endpoint issues, nothing in the pipeline currently consumes/validates it on subsequent requests (expected, since that's `F0002`, but means this slice's output format has no built-in consumer to validate it against yet).
- No exception-handling middleware anywhere in `ONG.API` — any unhandled exception in a new Handler (e.g. admin-not-found) will surface as a raw 500/developer exception page, not a clean 401/400, unless the Handler/Controller explicitly branches on it (`AnimalController.cs` currently has zero such branching to copy).
- `AdminSeeder.Seed` (`AdminSeeder.cs:20`) loads the admin via `context.Admins.OrderBy(a => a.CreatedAt).FirstOrDefault()` rather than filtering by username — it assumes a single-row table. A login lookup-by-username Handler must not copy this "just grab the first row" approach; it needs an actual `Username`-filtered query, and no such query exists yet anywhere in the codebase (`ONGDbContext.Admins` has no `Where(a => a.Username == ...)` precedent).
- `ONG.Tests.csproj` has no `ProjectReference` to `ONG.Application` or `ONG.API` today — any Handler/Controller-level test added in this slice requires a `.csproj` change, not just new test files.
- The unique index on `Admin.Username` (`ONGDbContext.cs:18-20`) is only proven enforced by the one Postgres-only integration test (`ONGDbContextTests.SavingSecondAdminWithDuplicateUsername_Throws`) — `EntityFrameworkCore.InMemory` (used by the rest of the suite, and likely by any new Handler unit tests) does not enforce it, so a login-lookup test using InMemory cannot rely on the DB to reject duplicate usernames.
- `docs/spec-driven-development.md` states the security standard "Auth on every endpoint" is currently aspirational (per `CLAUDE.md`'s Auth/multi-tenancy section) — `POST /auth/login` is explicitly the one endpoint expected to require no prior auth (it *is* the auth entry point per `F0001-admin-login.md:73-75`), so that general rule does not apply to this specific route.
