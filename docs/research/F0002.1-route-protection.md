## §2 — Execution Path

Current (unprotected) path for both target endpoints:

1. `AnimalController.Create(CreateAnimalCommand command)` (`AnimalController.cs:22`) → `_handler.Handle(command)` (L24, `CreateAnimalHandler`, registered in DI at `Program.cs:32`) → `Ok()` (L26). No auth check anywhere in this path.
2. `AnimalController.Adopt(Guid id)` (`AnimalController.cs:30`) → builds `AdoptAnimalCommand` (L32–35) → `_adoptHandler.Handle(command)` (L37, `AdoptAnimalHandler`, **not registered in DI** — see §1/§7) → `_repository.GetById` (`AdoptAnimalHandler.cs:17`) → throws bare `Exception("Animal not found.")` if null (L19–20, uncaught, no exception middleware in `ONG.API`) → else `animal.Adopt()` (L22, sets `Status`/`AdoptedAt` via private setters, `ONG.Domain/Entitites/Animal.cs:21-25`) → `_repository.SaveChanges()` (L24) → controller returns `Ok(animal)` (`AnimalController.cs:39`).
3. Token issuance path (the token this slice must start validating): `AuthController.Login(LoginCommand command)` (`AuthController.cs:18`) → `_handler.Handle(command)` (`LoginHandler.cs`, L29) → looks up admin by username, verifies password via `IPasswordHasher<Admin>.VerifyHashedPassword`, returns `null` on any failure (dummy-hash timing normalization on unknown username) → on success, `_tokenGenerator.GenerateToken(admin)` (`JwtTokenGenerator.cs:22`) returns a signed JWT with claims `sub=Username`, `adminId=Id`, HMAC-SHA256, expiry `Jwt:ExpiryMinutes` from now → `AuthController` returns `Ok(new LoginResult(token))` (200, body `{"token": "..."}`) or `Unauthorized(new { message = "Invalid username or password." })` (401) (`AuthController.cs:22-27`).
4. Nothing in the current pipeline consumes step 3's token: `Program.cs` has `UseAuthorization()` (L59) with no matching `AddAuthentication`/`UseAuthentication`, so `[Authorize]`, if added today, would have no scheme to authorize against and there is no scheme available at all currently (none is registered).

## §3 — Existing Patterns (reuse)

- **Fail-fast static `ValidateConfiguration` pattern** (`JwtTokenGenerator.cs:48-84`, mirrored from `AdminSeeder.ValidateConfiguration`, `back-end/ONG.Infrastructure/DataBase/AdminSeeder.cs:55-91`) — collects missing/invalid config keys into a `List<string>`, throws one `InvalidOperationException` listing all of them; called from `Program.cs` in the post-`Build()` scope block (L42-46), before any middleware registration.
- **`WebApplicationFactory<Program>` + config-swap + DbContext-swap pattern** (`LoginApiFactory.cs`, full file) — the only E2E test factory in the repo; swaps `ONGDbContext` to InMemory via double `RemoveAll` (L44-45) + `AddDbContext` re-registration (L47-48), and injects `Jwt:*`/`AdminSeed:*`/`PasswordHasher:*` config via `ConfigureAppConfiguration` (L20-32). A route-protection E2E test needing a valid bearer token would obtain one the same way `LoginEndpointTests` does — by POSTing to `/auth/login` through the same `HttpClient` first.
- **`IClassFixture<TFactory>` + `HttpClient` E2E test class shape** (`LoginEndpointTests.cs`, full file) — constructor takes the factory, calls `factory.CreateClient()` (L16); each `[Fact]` posts via `PostAsJsonAsync`, asserts `response.StatusCode`, optionally reads `ReadFromJsonAsync<JsonElement>()` and asserts on properties (`GetProperty(...).GetString()`).
- **`ITokenGenerator` interface** (`back-end/ONG.Application/Security/ITokenGenerator.cs:5-8`) — `string GenerateToken(Admin admin)`, implemented by `JwtTokenGenerator`, registered `AddScoped<ITokenGenerator, JwtTokenGenerator>()` (`Program.cs:34`). The claims/signing-key shape here (`Jwt:Key`, `HmacSha256`, `sub`/`adminId` claims, no `aud`) is exactly what a `TokenValidationParameters` for `AddJwtBearer` would need to mirror to accept these tokens.
- **Command+Handler, concrete-class DI registration (no interfaces for Handlers)** — every existing Handler (`CreateAnimalHandler`, `LoginHandler`) is registered as `AddScoped<ConcreteHandler>()`, not against an interface; controllers inject the concrete Handler type directly (`AnimalController.cs:11-12`, `AuthController.cs:10`).
- **`[ApiController]` automatic 400 on model-binding/validation failure** — `LoginCommand` (`back-end/ONG.Application/UseCases/Auth/Login/LoginCommand.cs`) uses `[Required]` data-annotation attributes; `LoginEndpointTests.Login_MissingPassword_Returns400` (L52-60) confirms `[ApiController]`'s automatic model-state validation already returns 400 with no custom code — this is the only existing precedent for input-validation error responses in the repo. `CreateAnimalCommand`/`AdoptAnimalCommand` have **no** validation attributes today (NFR1 in the parent spec — "valid token never substitutes for valid input" — has no existing 400-path precedent to reuse for `CreateAnimalCommand` specifically).

- Layering / structure: Command+Handler-per-use-case, concrete-class DI registration, repository interface in Application / implementation in Infrastructure, controllers stay thin (build Command, call one Handler, return result) — `AnimalController` currently does this with **zero validation or error branching** (`Create` discards the handler's return value and always returns bare `Ok()`; `Adopt` has no not-found handling at the controller level, relying on the handler's unhandled `throw`).
- Error handling: **no** custom exception types, **no** try/catch, **no** exception-handling middleware anywhere in `ONG.API` (confirmed no `ExceptionHandler`/`ProblemDetails`/`try{` pattern outside default `[ApiController]` behavior). ## §6 — Open Questions

> Collected, not answered — resolved in `design-slice`.

- Q1 — What exact `TokenValidationParameters` should `AddJwtBearer` use, given `JwtTokenGenerator.GenerateToken` (`JwtTokenGenerator.cs:37-41`) sets no `Audience`/`aud` claim? Should `ValidateAudience` be disabled, or should an audience be introduced on both the issuing and validating sides?
- Q2 — Should the JWT bearer scheme's signing key / issuer be read via the same raw `IConfiguration["Jwt:Key"]`/`["Jwt:Issuer"]` indexer pattern `JwtTokenGenerator` already uses, or via `IOptions<JwtOptions>` (no `Options` pattern exists anywhere in the codebase today for `Jwt:*`, confirmed — `Configure<PasswordHasherOptions>` at `Program.cs:35-36` is the only `Options`-pattern usage, for a different config section)?
- Q3 — Should the JWT bearer scheme's own validation config (key length, issuer, expiry format) reuse `JwtTokenGenerator.ValidateConfiguration` (already fail-fast for these same three keys) as-is, or does wiring `AddJwtBearer` need additional fail-fast checks of its own?
- Q4 — How should `AdoptAnimalHandler`'s not-found path (`AdoptAnimalHandler.cs:19-20`, bare `throw new Exception("Animal not found.")`, currently surfaces as an unhandled 500) be reconciled with adding `[Authorize]` to the same action — should this pre-existing gap be fixed in this slice (parent spec §6 only commits to fixing the *DI registration* gap, not the error-handling gap) or left as-is since it's a different defect than the DI one?
- Q5 — What HTTP status/body should an authenticated-but-invalid-input request to `Create` (`CreateAnimalCommand` has no validation attributes today, unlike `LoginCommand`) actually produce, given NFR1 requires "a valid token never substitutes for valid input" but no validation-attribute precedent exists on `CreateAnimalCommand` — does satisfying NFR1's test require adding validation attributes to `CreateAnimalCommand` as part of this slice, or does the existing behavior (whatever it is today for malformed bodies) already suffice?
- Q6 — Should `[Authorize]` be applied at the action level (`Create`/`Adopt` individually) or at the controller level (`[Authorize]` on the `AnimalController` class, matching the parent spec's framing of "protect two actions" but potentially simpler if every current/future action on this controller is meant to be admin-only)?
- Q7 — For the E2E sad-path tests (missing/invalid/expired/tampered token), does obtaining a "valid token" for the happy-path/valid-token-invalid-body tests require the test to call `/auth/login` first through the same `HttpClient` (mirroring how a real client would), or should the token be minted directly in-test via `JwtTokenGenerator`/`ITokenGenerator` (bypassing the login endpoint)? No precedent exists yet for either approach in this repo.
- Q8 — Does `AdoptAnimalHandler`'s DI registration fix (parent spec §6, "discovered while scoping this slice, since it's directly touched by the tests this slice needs") get added as `AddScoped<AdoptAnimalHandler>()` following the exact pattern of `CreateAnimalHandler`/`LoginHandler` (`Program.cs:32`/`L38`), or does anything about it warrant a different registration lifetime/shape?

## §7 — Risks / Gotchas

- **`AdoptAnimalHandler` DI gap is real and currently unhandled** (`Program.cs:1-46`, `AnimalController.cs:12,15`) — resolving `AnimalController` from the DI container today would throw `InvalidOperationException: Unable to resolve service for type 'AdoptAnimalHandler'...`. This means `POST /animals/{id}/adopt` is presumably broken/untested end-to-end in the running app today; any E2E test hitting this route before the registration is added will fail at container-resolution time, not at the assertion.
- **No exception-handling middleware anywhere in `ONG.API`** (`AdoptAnimalHandler.cs:19-20`) — the not-found path throws a bare `System.Exception`, which will surface as an unhandled 500 (or ASP.NET Core's dev exception page) rather than a clean 404/400, regardless of auth wiring. Adding `[Authorize]` does not change this behavior for authenticated requests to a nonexistent animal ID.
- **No `Audience`/`aud` claim on issued tokens** (`JwtTokenGenerator.cs:37-41`) — a naive `AddJwtBearer` + default `TokenValidationParameters` (which defaults `ValidateAudience = true`) would reject every token `JwtTokenGenerator` issues unless `ValidateAudience` is explicitly disabled or an audience is added to both sides.
- **`CreateAnimalCommand` has zero input-validation attributes** (`back-end/ONG.Application/UseCases/Animals/CreateAnimal/CreateAnimalCommand.cs`, confirmed in prior research and unchanged) — unlike `LoginCommand`'s `[Required]` fields, there is no existing precedent for what "invalid body" produces on this specific Command today; NFR1's "valid token + invalid body → 400" acceptance criterion may not currently hold even before this slice's changes.
- **`AnimalController.Create` discards the handler's return value** (`AnimalController.cs:22-27`) and always returns a bare `Ok()` regardless of outcome — any future assertion on the created-animal response body (not currently required by this slice's FRs) would need this changed too.
- **Both `.csproj` and NuGet-restore surface area grows**: adding `Microsoft.AspNetCore.Authentication.JwtBearer` touches `ONG.API.csproj` (or possibly `ONG.Infrastructure.csproj` if the scheme setup is factored out of `Program.cs` — no such extraction precedent exists in this repo; all DI/middleware setup lives inline in `Program.cs` today per `CLAUDE.md`'s own note that there are "no extension-method modules yet").
- **`docker-smoke-test` CI job exercises the real running app** (`.github/workflows/backend-docker.yml`, per `CLAUDE.md`) — if `[Authorize]` is misconfigured (e.g. wrong key/issuer wiring vs. `appsettings.json`'s `Jwt:Issuer = "ong-api"`, `Jwt:ExpiryMinutes = 60`), the Swagger-poll smoke test itself wouldn't directly catch an auth misconfiguration (it just polls `/swagger/v1/swagger.json`, not a protected route), but the `Category=Integration` test run in that same job would if a relevant test exists.
