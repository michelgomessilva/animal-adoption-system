## §2 — Execution Path

Current `GET /api/animals` path (no filters/sort yet — this slice's starting point):

1. `AnimalController.List()` (`AnimalController.cs:32`) — `[HttpGet]`, no parameters, no `[FromQuery]` anywhere.
2. → reads `HttpContext.User.Identity?.IsAuthenticated ?? false` (`AnimalController.cs:36`), builds `ListAnimalsCommand { IsAuthenticated }`.
3. → `ListAnimalsHandler.Handle(command)` (`ListAnimalsHandler.cs:17`) → `_repository.GetAll()` (`ListAnimalsHandler.cs:19`, no args) → ternary visibility filter applied **in-memory, after full materialization** (`ListAnimalsHandler.cs:21–23`).
4. → `AnimalRepository.GetAll()` (`AnimalRepository.cs:23–26`) → `_context.Animals.ToList()` → `ONGDbContext.Animals` (`ONGDbContext.cs:13`, `DbSet<Animal>`) → PostgreSQL (or InMemory in tests). No `.Where()`, no index on `Animal.Status` or any other column (`ONGDbContext.cs:16–21` only indexes `Admin.Username`).
5. → Controller returns `Ok(animals)` (`AnimalController.cs:41`) — raw `List<Animal>`, serialized via `System.Text.Json` with `JsonStringEnumConverter` (`Program.cs:23–28`).
6. Any unhandled `ArgumentException` anywhere in this path would be caught by `ExceptionHandlingMiddleware` (`Program.cs:107`, ahead of auth/controllers) and turned into `400` — this is the same mechanism `CreateAnimalHandler`'s enum guard clauses already rely on, but nothing in the current `List()` path throws today (no validation exists yet, since there's no input to validate).

## §3 — Existing Patterns (reuse)

- **Command + Handler shape** (`ListAnimalsCommand.cs` / `ListAnimalsHandler.cs`) — one folder under `UseCases/Animals/ListAnimals/`, handler constructor-injected with `IAnimalRepository`, registered by concrete type in `Program.cs:55`, called directly from the controller (no mediator).
- **In-memory `.Where()` filtering after `GetAll()`** (`ListAnimalsHandler.cs:19–23`) — the only existing example of narrowing the animal result set; happens in the Handler, not the repository, which today has zero query/filter parameters anywhere.
- **`ArgumentException` → `400` via `ExceptionHandlingMiddleware`** (`ExceptionHandlingMiddleware.cs:18–26`, used by `CreateAnimalHandler.cs:15–25`) — the only existing pattern in the codebase for signaling "invalid input" from a Handler up to an HTTP status code; no controller-level `BadRequest()` calls exist anywhere.
- **`DataAnnotations` + `[ApiController]` auto-400** (`CreateAnimalCommand.cs:8–30`, e.g. `[Required][StringLength(20)]` on `Name`) — the other existing 400 mechanism, driven by `[ApiController]`'s automatic `ModelState` validation on body-bound commands; confirmed by `AnimalControllerAuthTests.cs:147–167` (`Create_ValidTokenMissingName_Returns400`) and unit-tested directly via `Validator.TryValidateObject` in `back-end/ONG.Tests/Application/CreateAnimalCommandTests.cs:26–52`. This pattern has only ever been exercised for `[FromBody]`-bound commands, never `[FromQuery]`.
- **No response-DTO layer anywhere** — `List()` returns `List<Animal>` directly via `Ok(...)`, same as `Create`'s `StatusCode(201, animal)`. No `AnimalDto`/mapper type exists in the repo.
- **`LoginApiFactory` + `AnimalControllerAuthTests` E2E fixture** (`LoginApiFactory.cs`, full file) — reusable `WebApplicationFactory<Program>` swapping EF Core to InMemory, shared via `IClassFixture<LoginApiFactory>`; token minting/tampering helpers already exist (`AnimalControllerAuthTests.cs:60–81`).
- **Fake-repository unit-test pattern** — `ListAnimalsHandlerTests.cs` (`back-end/ONG.Tests/Application/`) uses a private nested `FakeAnimalRepository : IAnimalRepository`, mirroring `LoginHandlerTests.FakeAdminRepository`'s shape; would need a new `GetAll()`-seeding or filter-parameter shape if the repository interface changes.

## §5 — Observed Conventions

- Naming: `<Verb><Aggregate>Command`/`<Verb><Aggregate>Handler`, one folder per use case under `UseCases/<Aggregate>/<UseCase>/`. E2E test methods named `Method_Scenario_ExpectedResult` (e.g. `List_ValidToken_ReturnsAllAnimals`).
- Layering: Controllers thin (build Command → call Handler → return result); Handlers own orchestration/validation (guard clauses throwing `ArgumentException`); repositories are pure data-access, currently zero business logic and zero query parameters.
- Error handling: two distinct 400 mechanisms exist today — (1) `DataAnnotations` + `[ApiController]` auto-`ModelState` validation, only ever exercised on `[FromBody]` commands; (2) Handler-thrown `ArgumentException` → `ExceptionHandlingMiddleware` → `400` with `{ message }` body. No `[FromQuery]`-bound parameter, enum or otherwise, exists anywhere in the codebase to observe which of these (or neither) governs query-string binding failures.
- Tests: xUnit, `ONG.Tests/` split into `Api/` (E2E via `WebApplicationFactory`), `Application/` (handler/command unit tests, hand-written fakes, no mocking library), `Domain/`, `Infrastructure/` (EF Core InMemory). Run via `dotnet test ONG.slnx --filter "Category!=Integration"` for the fast/non-Postgres subset.
- Authorization: **no role-based authorization exists anywhere in the codebase** — grep for `IsInRole`, `ClaimTypes.Role`, `[Authorize(Roles=...)]` returns zero matches. The only identity distinction anywhere is `HttpContext.User.Identity?.IsAuthenticated` (boolean). There is exactly one seeded `Admin` identity type in the system (`AdminSeeder`), so "authenticated" and "the parent spec's admin-only status filter" currently have no distinct representation in code — being authenticated at all is the only signal available.

## §6 — Open Questions

- Q1 — The parent spec's `status` filter is described as "admin-only," but no role/claim distinguishes "admin" from "any authenticated caller" anywhere in the codebase (§5) — how (or whether) this slice should represent that distinction is undetermined.
- Q2 — Whether filter parameters should be applied in-memory after `GetAll()` (following `ListAnimalsHandler`'s existing `.Where()` pattern) or pushed into `IAnimalRepository`/`AnimalRepository` as query parameters (`IQueryable`-based) — no precedent exists for the latter anywhere in the repo (`IAdminRepository`'s single method also takes no filter-composition pattern to follow).
- Q3 — How an invalid filter or `orderBy` value should signal `400` — via a thrown `ArgumentException` (mirroring `CreateAnimalHandler`'s existing pattern, already wired through `ExceptionHandlingMiddleware`) or via `[FromQuery]`+`[ApiController]` automatic `ModelState` validation (the `DataAnnotations` pattern, but never exercised on query-string parameters in this codebase) — both mechanisms exist today for different input sources, neither has been used for query-string enum parsing.
- Q4 — What ASP.NET Core's default `[FromQuery]` model binder actually does with an invalid enum string (e.g. `?species=Elephant`) in this specific app configuration — not observed in this codebase, since no `[FromQuery]` binding exists anywhere yet (§1, §5).
- Q5 — The parent spec (FR5) states an anonymous caller's `status` filter value "can never widen the result past `Available`" but doesn't specify the exact composition: silently ignore the `status` filter for non-authenticated callers vs. apply the filter but intersect with `Available` — undetermined from the code (no such branching exists today).
- Q6 — What `ListAnimalsCommand`'s shape should become once it needs to carry filter/sort parameters (currently a single `bool IsAuthenticated`, not model-bound) — whether new properties are added directly to it, bound via `[FromQuery]` in the controller, or a separate query/filter object is introduced — no precedent exists since this is the codebase's first query-string-bound input of any kind.
- Q7 — The exact `orderBy` value grammar and sortable-field set (parent spec FR6 explicitly defers this) — no existing sort implementation anywhere in the codebase to draw a convention from.

## §7 — Risks / Gotchas

- `Animal.cs:19–42` — the constructor still never assigns `Species = species` (unfixed since F0003.1's research). Every persisted `Animal`'s `Species` is stuck at `Species.None` regardless of what was passed at creation. A `species` filter built against real data will find **zero results for `Dog`/`Cat`** and only ever match `None` — this is a functional risk specific to this slice (F0003.1's read endpoint merely displayed the wrong value; F0003.2's species filter would appear entirely broken against real persisted data) unless this defect is addressed first.
- `ONGDbContext.cs:16–21` — no index exists on `Animal.Status`, `Species`, `Sex`, `Size`, `District`, or `City` (only `Admin.Username` is indexed). Any filter combination on these columns is a full table scan — accepted at NFR2's stated MVP scale, but now directly relevant since this slice adds the first filtered queries against these columns.
- `District`/`City` are free-text `string` with `[StringLength(30)]` validation only on the *create* command (`CreateAnimalCommand.cs:24–30`), not on the entity itself, and no case-normalization or trimming is observed anywhere. A district/city filter based on exact string equality could behave surprisingly with casing/whitespace differences — not yet exercised by any code or test.
- `AnimalControllerAuthTests.cs` — all `[Fact]`s in this class share one `IClassFixture<LoginApiFactory>` database instance and xUnit does not guarantee declaration-order execution (documented already in `docs/features/F0003.1-animal-listing-endpoint.md` §5 Task 3 as a known, worked-around risk). Any new filter/sort E2E tests added to this same file must account for animals seeded by other `[Fact]`s in the class if they run first — the existing `List_EmptyCatalogNoToken_...` test already works around this by asserting shape (`JsonValueKind.Array`) rather than literal emptiness.
- `IAnimalRepository.GetAll()` / `AnimalRepository.GetAll()` (`AnimalRepository.cs:23–26`) is fully synchronous, matching `Add`/`SaveChanges` — no `async`/`Task`/`CancellationToken` anywhere in this repository; any signature change for filter parameters will need to decide whether to preserve this (F0003.1's Q2 already resolved sync for `GetAll()` with no parameters — this slice reopens the question if the repository's signature changes at all).
