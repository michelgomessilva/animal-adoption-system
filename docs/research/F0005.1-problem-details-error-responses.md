## §2 — Execution Path

Current error-response paths (four divergent shapes, confirmed independently for each):

1. **Unhandled exception path:** Any request → `ExceptionHandlingMiddleware.InvokeAsync` (`ExceptionHandlingMiddleware.cs:12`) wraps `_next(context)` (L16). If the downstream pipeline/action throws `ArgumentException`, caught at L18, writes 400 + `{ message = ex.Message }`. Any other `Exception`, caught at L27, writes 500 + `{ message = "An unexpected error occurred." }`. This middleware runs first in the pipeline (`Program.cs:132`), so it wraps every later stage including `ClientTokenEnforcementMiddleware`, `UseAuthentication`/`UseAuthorization`, and all controller actions.
2. **Client-token enforcement path:** Request (not `POST /oauth/token`) → `ClientTokenEnforcementMiddleware.InvokeAsync` (`ClientTokenEnforcementMiddleware.cs:23`, registered `Program.cs:137`, runs after CORS/before auth) → reads `X-Client-Token` header (L32) → missing+enforced → 401 (L38); present → `IClientTokenValidator.Validate` (`ClientTokenValidator.cs`, implementation of `IClientTokenValidator` at `ONG.Application/Security/IClientTokenValidator.cs:10-13`) returns `ClientTokenValidationStatus` (`StructurallyInvalid`/`SemanticallyInvalid`/`Valid`, enum at `IClientTokenValidator.cs:3-8`) → `StructurallyInvalid` → 400 (L48–50); `SemanticallyInvalid` → 401 (L51–53); `Valid` → falls through to `_next(context)` (L56).
3. **Invalid-credentials path (`AuthController.Login`):** `POST /auth/login` → `AuthController.Login` (`AuthController.cs:18`) → `LoginHandler.Handle(command)` (L20) → `result is null` → `Unauthorized(new { message = "Invalid username or password." })` (L24). Runs inside the MVC/`ControllerBase` context (`[ApiController]`, L6), unlike the two middleware paths above.
4. **Invalid-credentials path (`OAuthController.Token`):** `POST /oauth/token` → `OAuthController.Token` (`OAuthController.cs:18`) → `IssueClientTokenHandler.Handle(command)` (L20) → `result is null` → `Unauthorized(new { message = "Invalid client_id or client_secret." })` (L24). Same MVC context, same anonymous-object shape as #3, but independently written (no shared helper).
5. **Not-found path (`AnimalController.GetById`/`Update`):** `GET/PUT /api/animals/{id}` → handler returns `null` → bare `return NotFound();` (`AnimalController.cs:65` and `:78`) — no body, no `Content-Type` beyond ASP.NET Core's default empty-204/404 handling.

## §3 — Existing Patterns (reuse)

- `[ApiController]` attribute on all three controllers (`AuthController.cs:6`, `OAuthController.cs:6`, `AnimalController.cs:11`) — enables `ControllerBase.Problem(...)`/`ValidationProblem(...)` helpers and automatic `ProblemDetailsFactory` injection into MVC context, though neither is currently used anywhere (confirmed zero hits for `Problem(` / `ValidationProblem(` across `back-end/ONG.API/Controllers/`).
- `IOptions<T>` binding pattern: `builder.Services.Configure<ClientAuthOptions>(builder.Configuration.GetSection("ClientAuth"))` (`Program.cs:94-95`), mirroring `Configure<PasswordHasherOptions>` (`Program.cs:92-93`) — the existing precedent for any new options-class binding.
- `ClientAuthOptions` (`back-end/ONG.API/Middleware/ClientAuthOptions.cs:1-7`) — a plain POCO options class (`public bool EnforcementEnabled { get; set; }`), the shape any similar options class in this codebase follows.
- Custom middleware shape: constructor takes `RequestDelegate next` (+ optionally `IOptions<T>`), `InvokeAsync(HttpContext context, ...)` method, private static `WriteStatus`-style helper for building an ad-hoc JSON error body (`ClientTokenEnforcementMiddleware.cs:59-63`) — the precedent for how middleware currently writes error responses directly via `HttpContext.Response`.
- `WriteAsJsonAsync(new { ... })` — the only response-writing mechanism used by both existing middlewares (`ExceptionHandlingMiddleware.cs:22-25,32-35`; `ClientTokenEnforcementMiddleware.cs:62`); no use of `Results.Problem(...)`, `TypedResults`, or ASP.NET Core minimal-API result helpers anywhere in the codebase.
- Fail-fast `ValidateConfiguration(IConfiguration)` static-method pattern (`JwtTokenGenerator.cs`, `ClientCredentialsProvider.cs`), invoked from `Program.cs:106-108` inside the pre-pipeline `CreateScope()` block (`Program.cs:104-121`) — the established pattern for any new startup-time configuration validation, though `AddProblemDetails()` itself requires no config keys.

## §5 — Observed Conventions

- Naming: no existing convention for ProblemDetails-related naming (green field for this slice) — the only related precedent is the ad-hoc `{ message }` anonymous-object shape repeated independently in `ExceptionHandlingMiddleware`, `ClientTokenEnforcementMiddleware`, `AuthController`, and `OAuthController` (four separate call sites, no shared constant/helper/type between them).
- Layering / structure: error-response construction happens inline at the point of failure in every case observed — no centralized error-response builder, no shared "problem factory" service, no base controller class. Middleware-level errors (`ExceptionHandlingMiddleware`, `ClientTokenEnforcementMiddleware`) write directly to `HttpContext.Response`; controller-level errors (`AuthController`, `OAuthController`, `AnimalController`) use `ControllerBase` action-result helpers (`Unauthorized(...)`, `NotFound()`).
- Error handling: `ArgumentException` (business validation failures thrown by handlers, e.g. `CreateAnimalHandler.cs`, `UpdateAnimalHandler.cs`, `ListAnimalsHandler.cs` — all under `ONG.Application/UseCases/`) is the only handler-thrown exception type observed anywhere; no custom exception types exist in the codebase (confirmed zero classes deriving from `Exception`/`ApplicationException`/`SystemException` in `ONG.Domain`, `ONG.Application`, `ONG.API`). All other `throw new InvalidOperationException(...)` sites (`JwtTokenGenerator.cs`, `ClientCredentialsProvider.cs`, `AdminSeeder.cs`) are startup-time fail-fast validators, not HTTP-request-time errors, and are not caught by `ExceptionHandlingMiddleware` in the normal request path (they execute before the pipeline is built, inside `Program.cs:104-121`).
- Tests: xUnit, `ONG.Tests` project, `Api/` subfolder for E2E tests via `WebApplicationFactory<Program>`. Every E2E test reads response bodies via `await response.Content.ReadFromJsonAsync<JsonElement>()` (uniform pattern, no anonymous-type/named-DTO deserialization, no raw string parsing) then accesses fields via `body.GetProperty("...")`. No test anywhere currently asserts `Content-Type`. Run via `dotnet test ONG.slnx --filter "Category!=Integration"`.

## §7 — Risks / Gotchas

- Four independent call sites currently build the `{ message }` shape by hand (`ExceptionHandlingMiddleware.cs:22-25,32-35`; `ClientTokenEnforcementMiddleware.cs:62`; `AuthController.cs:24`; `OAuthController.cs:24`) — changing all four to a consistent `ProblemDetails` shape touches every one of them; missing any one leaves an inconsistent response shape, defeating the feature's stated purpose (parent spec FR1).
- Nine existing E2E tests read the current `message` property directly via `JsonElement.GetProperty("message")` (`LoginEndpointTests.cs:47`, `OAuthEndpointTests.cs:50`, `AnimalControllerAuthTests.cs:319,329`) — these will start throwing `KeyNotFoundException`-equivalent (`JsonElement.GetProperty` throws if the property is absent) the moment the response shape changes, unless updated in the same change.
- `ExceptionHandlingMiddleware`'s generic `catch (Exception)` (`ExceptionHandlingMiddleware.cs:27`) discards the caught exception entirely (no logging, no variable binding) — the parent spec's NFR requires the 500 `detail` to stay a fixed generic string (not `ex.Message`); this existing behavior already satisfies that, but any refactor to use `AddProblemDetails()`'s built-in unhandled-exception handling must preserve not leaking the real exception message/stack trace in the 500 body.
- `ExceptionHandlingMiddleware` (`Program.cs:132`) is registered **before** `ClientTokenEnforcementMiddleware` (`Program.cs:137`) and before `UseAuthentication`/`UseAuthorization` (`Program.cs:139-140`) — it wraps everything downstream, so it is the natural place to also catch anything unexpected inside the newer middleware or MVC pipeline, but its own hand-written JSON body must be reconciled with whatever ProblemDetails-construction approach is chosen for consistency (parent spec NFR3 explicitly requires "one documented pattern, not two" between middleware and controllers).
- No test in the suite exercises `AnimalController.GetById`/`Update`'s not-found path at all (confirmed zero matches for `api/animals/` or `GetById`/`Update` method names anywhere in `ONG.Tests`) — this is a pure test-coverage gap that pre-dates this slice; any new/changed behavior here has zero existing regression protection to lean on.
- `ClientTokenEnforcementMiddleware`'s `Valid` case in its `switch` (`ClientTokenEnforcementMiddleware.cs:46-54`) has no explicit `case` — it relies on falling through past the `switch` block to `_next(context)` (L56) for both `Valid` and any future unhandled enum value; this is pre-existing behavior, not something this slice needs to touch, but worth noting since this slice will edit the same file's error-writing paths (L38, L49, L52) and must not disturb this fallthrough.
