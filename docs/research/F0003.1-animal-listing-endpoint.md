## §2 — Execution Path

Current write path (`POST /api/animals`), the only existing precedent for this slice's read path:

1. `AnimalController.Create` (`AnimalController.cs:19`) — `[Authorize][HttpPost]`, binds `CreateAnimalCommand` from body.
2. → `CreateAnimalHandler.Handle(command)` (`CreateAnimalHandler.cs:13`, called synchronously, not injected via interface) — validates required enums via manual `== EnumType.None` checks that `throw new ArgumentException(...)` (L15–25), constructs `new Animal(...)` (L28–39), calls `_repository.Add(animal)` then `_repository.SaveChanges()` (L41–42), returns the entity (L44).
3. → `AnimalRepository.Add`/`SaveChanges` (`AnimalRepository.cs:15–22`) → `ONGDbContext.Animals` (`ONGDbContext.cs:13`, `DbSet<Animal>`) → PostgreSQL (or InMemory provider in E2E tests).
4. → Controller returns `StatusCode(201, animal)` (`AnimalController.cs:24`) — raw entity serialized via `System.Text.Json` with `JsonStringEnumConverter` (`Program.cs:22–27`).
5. Any unhandled exception (e.g. the handler's `ArgumentException`) is caught by `ExceptionHandlingMiddleware`, registered before `UseAuthentication`/`UseAuthorization`/`MapControllers` (`Program.cs:105–111`) and thus wraps the whole downstream pipeline.

No GET/read path exists anywhere in the codebase today — `IAnimalRepository` has no query method (`IAnimalRepository.cs:7–8`), and grepping the full `back-end` tree for `IsAuthenticated`, `AllowAnonymous`, `User.Identity` returns zero matches.

## §3 — Existing Patterns (reuse)

- **Command + Handler shape** (`ONG.Application/UseCases/Animals/CreateAnimal/CreateAnimalCommand.cs` + `CreateAnimalHandler.cs`) — Command is a plain class with `System.ComponentModel.DataAnnotations` attributes; Handler is constructor-injected with the repository interface, exposes one public `Handle(...)` method, registered in `Program.cs` via `AddScoped<XHandler>()` by concrete type (no interface).
- **Repository interface/impl split** (`IAnimalRepository.cs` / `AnimalRepository.cs`) — interface in `ONG.Application/Repositories/`, implementation in `ONG.Infrastructure/Repositories/`, constructor-injects `ONGDbContext`.
- **No response-DTO layer anywhere in the codebase** — both `AnimalController.Create` and `AuthController`'s login action return handler results (raw entity / result object) directly; there is no `AnimalDto`/`AnimalResponse`/mapper type in the repo (confirmed by explore agent's glob/grep, no matches).
- **`WebApplicationFactory<Program>` + `LoginApiFactory`** (`ONG.Tests/Api/LoginApiFactory.cs`) — reusable fixture already swaps `ONGDbContext` to EF Core InMemory and injects test JWT/AdminSeed config; shared via `IClassFixture<LoginApiFactory>`.
- **Token minting/tampering test helpers** (`AnimalControllerAuthTests.cs:48–80`) — `GetValidTokenAsync()`, `MintExpiredToken()`, `TamperToken()` already exist and can mint valid/expired/tampered tokens for E2E auth-branch testing.
- **`CountPersistedAnimals()` DB-scope helper** (`AnimalControllerAuthTests.cs:82–87`) — pattern for reading `ONGDbContext` directly inside a test via `factory.Services.CreateScope()`.
- **`[Trait("Category","Integration")]` convention** — only `ONGDbContextTests.cs:14` uses it (for a Postgres-only unique-index test); every other test (including all InMemory-backed E2E/unit tests) has no trait and runs in the default/CI-fast filter.
- **`ExceptionHandlingMiddleware`** (`ONG.API/Middleware/ExceptionHandlingMiddleware.cs`, exists, not read in full during this research pass — see §8) — already registered in the pipeline (`Program.cs:105`) ahead of auth/controllers, and is what turns `CreateAnimalHandler`'s `ArgumentException` throws into an HTTP 400 today (inferred from the `Create_ValidTokenMissingName_Returns400` test passing against a DataAnnotations validation failure, not an ArgumentException — the exact mapping was not traced end-to-end, see §8).

## §5 — Observed Conventions

- Naming: Command/Handler pairs named `<Verb><Aggregate>Command`/`<Verb><Aggregate>Handler` (e.g. `CreateAnimalCommand`/`CreateAnimalHandler`), one folder per use case under `UseCases/<Aggregate>/<UseCase>/`. E2E test methods named `Method_Scenario_ExpectedResult` (e.g. `Create_ValidToken_Returns201`).
- Layering / structure: Controllers are thin (build Command → call one Handler → return result); Handlers own orchestration and manual validation (`== EnumType.None` guard clauses throwing `ArgumentException`); repositories are pure data-access with no business logic. All existing repository methods are synchronous (no `async`/`Task`/`CancellationToken` anywhere in `IAnimalRepository`/`AnimalRepository`).
- Error handling: Handler-level guard clauses throw `ArgumentException` for missing enum values (`CreateAnimalHandler.cs:15–25`); `ExceptionHandlingMiddleware` sits ahead of auth/controllers in the pipeline and is presumed to translate exceptions to HTTP responses (not traced in this pass, see §8). The controller itself has no explicit not-found/validation branching — `AuthController`'s login action is the only precedent for `if (result is null) return Unauthorized(...)` style branching in a controller.
- Tests: xUnit, `ONG.Tests/` split into `Api/` (E2E via `WebApplicationFactory<Program>` + `LoginApiFactory`), `Application/` (handler/command unit tests, hand-written fakes, no mocking library), `Domain/` (entity unit tests), `Infrastructure/` (repository/seeder/config tests against EF Core InMemory, one Postgres-only test tagged `[Trait("Category","Integration")]`). Run via `dotnet test ONG.slnx` (all) or `dotnet test ONG.slnx --filter "Category!=Integration"` (fast/CI-build-job subset).

## §6 — Open Questions

- Q1 — Whether the new read method belongs on `IAnimalRepository` as a single method returning all animals (with filtering done in the Handler/in-memory) or as a method that already takes a status-visibility parameter (filtering done in the repository/EF Core query) — the existing interface has no precedent for either shape since it has zero query methods today.
- Q2 — Whether `Handle`/the new repository method should be made `async`/`Task`-returning (introducing the codebase's first async data-access call) or follow the existing fully-synchronous convention (`Add`/`SaveChanges` are both sync).
- Q3 — Whether the response continues the "return raw entity" convention (no DTO layer exists anywhere yet) or this slice introduces the first response-shaping type — relevant because `Animal.Species` is currently never actually persisted correctly (§7, Animal.cs constructor bug) and because NFR1 says "reuses the existing entity's public fields... unless the design phase finds a reason."
- Q4 — How the controller should read `HttpContext.User.Identity?.IsAuthenticated` and pass that (or the resulting visibility filter) into the Command/Handler — there is zero precedent for this anywhere in the codebase (confirmed via grep: no `IsAuthenticated`/`AllowAnonymous`/`User.Identity` usage exists).
- Q5 — Whether `[Authorize]` should be entirely absent from the new action (relying only on the `IsAuthenticated` check inside) or whether some ASP.NET Core mechanism (e.g. an optional-auth policy) is more idiomatic for "endpoint doesn't require auth but branches behavior on it" — no existing example of this pattern in the repo.
- Q6 — Whether E2E tests for this slice should reuse `AnimalControllerAuthTests`/`LoginApiFactory` as-is (adding new `[Fact]`s to the existing class or a new sibling test class) — both are structurally reusable but the exact placement wasn't decided here.

## §7 — Risks / Gotchas

- `Animal.cs:19–42` — the constructor takes a `species` parameter but its body never assigns `Species = species;` (only `Sex, Size, ApproximateAge, Description, Image, CreatedAt, Status, District, City` are set). Every `Animal` ever constructed via this constructor has `Species` stuck at its default enum value (`Species.None`), regardless of what's passed at creation time. This is a **pre-existing bug** that predates this slice — any new read endpoint returning `Animal.Species` will surface this as visibly wrong data (every animal shows `Species: "None"`), which is likely to be noticed immediately once a listing endpoint exists. Not attributable to this slice's changes, but the design phase needs to know it exists.
- `AnimalController.cs:17` — `[Authorize]` is the only authorization primitive currently used in the codebase; there is no existing example of a controller action that is reachable both anonymously and by an authenticated caller with different behavior. FR1/FR4 of the parent spec require exactly this shape (publicly reachable, no 401 on bad/missing token) — implementing it will be the first departure from the all-or-nothing `[Authorize]` pattern.
- `IAnimalRepository.cs`/`AnimalRepository.cs` — fully synchronous today (`Add`, `SaveChanges`, no `Task`/`CancellationToken` anywhere). Introducing an async read method would be the first async data-access code in the repo and would deviate from the existing convention; introducing a sync one keeps consistency but diverges from typical ASP.NET Core/EF Core guidance.
- `ONGDbContext.cs:16–21` — `OnModelCreating` only configures an index on `Admin.Username`; there is no index on `Animal.Status` (or any other `Animal` column). A listing query filtered by `Status` will do a full table scan — acceptable at current/expected MVP scale per NFR2 ("no pagination... educational project, small expected dataset") but worth having on record.
- `LoginApiFactory.cs:44–45` — EF Core InMemory swap requires removing *both* `DbContextOptions<ONGDbContext>` and `IDbContextOptionsConfiguration<ONGDbContext>` service descriptors; the code comment (L36–43) documents this as a non-obvious two-descriptor gotcha already solved once — relevant if this slice's tests need any further factory customization.
- Test-side: `ExceptionHandlingMiddleware` (`ONG.API/Middleware/ExceptionHandlingMiddleware.cs`) exists and sits ahead of auth/controllers in the pipeline, but its exact exception→status-code mapping was not traced in this research pass (see §8) — the design phase should not assume a specific mapping without checking that file directly if the new Handler needs to signal an error condition (though FR1–FR4 for Slice 1 describe no error paths beyond "always 200," so this may be moot for this specific slice).
