## §2 — Execution Path

Current path for the two protected routes (admin JWT only — no client-token check exists anywhere yet):

1. Request arrives → `ExceptionHandlingMiddleware.InvokeAsync` (`ExceptionHandlingMiddleware.cs:12`) wraps everything downstream.
2. → `UseCors(OpenCorsPolicy)` (`Program.cs:130`) — `AllowAnyOrigin/AllowAnyHeader/AllowAnyMethod` (`Program.cs:30-36`), runs before auth.
3. → `UseAuthentication()` (`Program.cs:132`) — the single `AddJwtBearer` scheme (`Program.cs:76-89`) attempts to validate any `Authorization: Bearer ...` header against `ValidIssuer = Jwt:Issuer` (`"ong-api"`) and `Jwt:Key`. A token minted by `GenerateClientToken` (issuer `"ong-api-oauth-clients"`) would **fail** this scheme's issuer check today, since only one scheme exists and it pins `ValidIssuer` to the admin issuer.
4. → `UseAuthorization()` (`Program.cs:133`) — evaluates `[Authorize]` where present (`AnimalController.Create`/`Update` only).
5. → `MapControllers()` (`Program.cs:135`) → matched controller action executes. `GetById`/`List` and `OAuthController.Token`/`AuthController.Login` currently run with no token requirement of any kind, client or admin.
6. → Response returned; `ExceptionHandlingMiddleware`'s catch blocks translate unhandled `ArgumentException`→400 / other `Exception`→500 if the action throws.

There is currently **no code path anywhere** that validates a client token (`ClientTokenIssuer`-issued JWT) on any route — F0004.1 only issues it; nothing consumes/validates it yet.

## §3 — Existing Patterns (reuse)

- Fail-fast `ValidateConfiguration(IConfiguration)` static-method pattern (`JwtTokenGenerator.cs:65-101`, `ClientCredentialsProvider.cs` L30-69 per prior slice, `AdminSeeder.cs` L55-91) — accumulate a `List<string> missing`, add descriptive entries, throw one `InvalidOperationException` naming every missing/invalid key; all three are invoked from `Program.cs:102-115` before `Migrate()`/`AdminSeeder.Seed`.
- `AddJwtBearer` single-scheme registration shape (`Program.cs:76-89`) — the only existing JWT-validation wiring in the app; reads `Jwt:Issuer`/`Jwt:Key` directly off `builder.Configuration`.
- `ExceptionHandlingMiddleware` (`ExceptionHandlingMiddleware.cs:1-39`) — the only custom ASP.NET Core middleware in the repo; demonstrates the `RequestDelegate _next` / `InvokeAsync(HttpContext)` shape and how to set `context.Response.StatusCode` + `WriteAsJsonAsync` for a specific status (400) distinct from the catch-all 500.
- `[Authorize]` action-attribute usage (`AnimalController.cs:32,69`) — the only existing authorization-enforcement mechanism; no policies, no `AddAuthorization()` call, no `IAuthorizationHandler`, no action filters (`IActionFilter`/`IAsyncActionFilter`) exist anywhere in the codebase (confirmed via repo-wide search).
- `Configure<PasswordHasherOptions>(builder.Configuration.GetSection("PasswordHasher"))` (`Program.cs:91-92`) — the only `IOptions<T>` binding in the codebase; no `GetValue<bool>(...)` call exists anywhere in `back-end/`, so there is no existing precedent for reading a boolean feature flag from config.
- `LoginApiFactory`/`OAuthApiFactory` (`back-end/ONG.Tests/Api/*.cs`) `WebApplicationFactory<Program>` subclasses with `ConfigureAppConfiguration`+`AddInMemoryCollection` — the mechanism for injecting any new test-only config value (including a hypothetical enforcement flag) into E2E tests.
- `AnimalControllerAuthTests.cs` (`back-end/ONG.Tests/Api/AnimalControllerAuthTests.cs`, 348 lines) — existing E2E precedent for testing bearer-token behavior against a protected route: valid/missing/malformed/expired/tampered token cases, using locally-minted tokens (`MintExpiredToken()`, `TamperToken(string)` helpers) and `_client.DefaultRequestHeaders.Authorization = new AuthenticationHeaderValue("Bearer", token)`. Its `Create_MalformedToken_Returns401` test sends `Authorization: Bearer not-a-jwt` and asserts `401` (not 400) — i.e. today's `AddJwtBearer` handler treats an unparsable *token* as 401, not 400; this is distinct from a malformed *header* (e.g. missing the `Bearer` scheme entirely), which the parent spec's NFR3 requires to be `400`.
- `CorsPolicyTests.cs` (`back-end/ONG.Tests/Api/CorsPolicyTests.cs`, 46 lines) — E2E precedent for asserting behavior of an `OPTIONS` CORS-preflight request against a protected route, asserting it is *not* rejected with 401/403 (L40-41) — relevant since CORS (`UseCors`, `Program.cs:130`) runs before any auth middleware today.
- `ClientCredentialsStartupFailureTests.cs` (`back-end/ONG.Tests/Api/ClientCredentialsStartupFailureTests.cs`, 54 lines) — E2E precedent for proving a fail-fast validator crashes host startup: builds a raw `WebApplicationFactory<Program>` with a required config section omitted, asserts `Assert.ThrowsAny<Exception>(() => factory.CreateClient())`.
- `docker-compose.yml`'s `${VAR:?message}` interpolation (`back-end/docker-compose.yml:8-10,30-34`) and the `AdminSeed__*`/`Jwt__*`/`ClientCredentials__*` double-underscore env-var-to-`IConfiguration`-section convention — the precedent for wiring any new config key through Docker Compose, `.env`/`.env.example`, CI, and Render.

## §5 — Observed Conventions

- Naming: fail-fast validators are named `ValidateConfiguration(IConfiguration)`, static, on the Infrastructure implementation class (`JwtTokenGenerator`, `ClientCredentialsProvider`, `AdminSeeder`) — never on the Application interface.
- Layering / structure: config-reading always happens in `ONG.Infrastructure` (or directly in `Program.cs`'s composition root); `ONG.Application` never touches `IConfiguration` directly — it depends on an interface (`IClientCredentialsProvider`, `ITokenGenerator`) implemented in Infrastructure. Handlers are plain classes registered individually via `AddScoped<XHandler>()` in `Program.cs` (no MediatR).
- Error handling: `[ApiController]` automatic `ModelState` validation produces 400 for `[Required]`/`[RegularExpression]` failures (used by `IssueClientTokenCommand`); explicit `Unauthorized(new { message = "..." })` for credential mismatches (`OAuthController.cs:24`, `AuthController.Login`'s equivalent); `ExceptionHandlingMiddleware` is the last-resort translator for `ArgumentException`→400/`Exception`→500 for anything an action throws unhandled.
- Tests: xUnit, `ONG.Tests` project, organized under `Api/` (E2E via `WebApplicationFactory<Program>`), `Application/` (handler unit tests), `Infrastructure/` (provider/generator unit tests), `Domain/` (entity unit tests). Run via `dotnet test ONG.slnx --filter "Category!=Integration"` (excludes the one Postgres-dependent test). E2E tests use `IClassFixture<TFactory>` with a shared `WebApplicationFactory<Program>` subclass per test-suite family (`LoginApiFactory`, `OAuthApiFactory`).

## §6 — Open Questions

- Q1 — How should a client token (issuer `ong-api-oauth-clients`) actually be *validated* on a route, given the existing `AddJwtBearer` scheme (`Program.cs:76-89`) is pinned to `ValidIssuer = Jwt:Issuer` (the admin issuer) and would reject a client token today? (second `AddJwtBearer` scheme + policy-based selection vs. manual token validation vs. custom middleware — unresolved.)
- Q2 — Where does the new `ClientAuth:EnforcementEnabled`-shaped flag (FR5, defaulting to disabled) get read, and what shape (middleware short-circuit vs. conditional scheme registration vs. something else)? No `GetValue<bool>(...)` precedent exists anywhere in the codebase today (§3).
- Q3 — How is the token endpoint (`POST /oauth/token`) exempted from global enforcement — no `[AllowAnonymous]` attribute exists anywhere in the codebase today, so there's no established precedent for an exemption mechanism.
- Q4 — What produces the required clean `400` for a malformed Authorization header (missing `Bearer` scheme, etc.), given the existing `AddJwtBearer` handler's behavior for an unparsable *token value* is `401`, not `400` (observed in `AnimalControllerAuthTests.Create_MalformedToken_Returns401`)? Whether the distinction is "header not in `Bearer <token>` form" vs. "token value doesn't parse as a JWT" is unresolved, and which layer detects it (middleware vs. auth handler `OnAuthenticationFailed`/`OnChallenge` events) is unresolved.
- Q5 — Does enforcement apply per-route via `[Authorize(...)]`-style attributes added to every existing action, or as blanket pipeline middleware applied to all requests? No global/controller-level `[Authorize]`, `AddAuthorization()` policy, or action filter exists anywhere today to extend.
- Q6 — How does global enforcement interact with the CORS preflight `OPTIONS` request, given `UseCors` (`Program.cs:130`) already runs before `UseAuthentication`/`UseAuthorization` (`Program.cs:132-133`) and `CorsPolicyTests.cs` already asserts a preflight against a protected route is not rejected with 401/403 — must a client-token-enforcing layer also exempt `OPTIONS` preflights, or does ASP.NET Core's CORS middleware already short-circuit them before reaching that layer?
- Q7 — Exact config key names/shape for the new flag and any client-token-scheme-specific settings (e.g. a distinct `ClientAuth:*` section vs. reusing `ClientCredentials:*`) — undecided; no existing key named anything like `ClientAuth` appears in `appsettings.json`, `.env.example`, `docker-compose.yml`, or the CI workflow today.

## §7 — Risks / Gotchas

- `AddJwtBearer` currently registers exactly **one** scheme validating only the admin issuer (`Program.cs:76-89`) — a client token minted by `GenerateClientToken` is **not currently accepted by any existing auth mechanism**; adding client-token support is net-new validation logic, not a toggle on existing logic.
- `AnimalController.List` (`AnimalController.cs:42-50`) manually branches on `HttpContext.User.Identity?.IsAuthenticated` (L45) to decide whether to show non-`Available` animals — if a new client-token scheme is added alongside the existing admin scheme, this line's meaning could shift (an authenticated *client* is not the same as an authenticated *admin*) depending on how the new scheme is wired; today `IsAuthenticated` only ever reflects the admin JWT scheme succeeding.
- `UseCors(OpenCorsPolicy)` (`Program.cs:130`) runs **before** `UseAuthentication`/`UseAuthorization` (`Program.cs:132-133`) — any new enforcement layer inserted between `UseCors` and `MapControllers` must not break the existing CORS-preflight-not-rejected behavior asserted by `CorsPolicyTests.cs`.
- `ExceptionHandlingMiddleware` (`Program.cs:127`) is registered **before** `UseCors`, meaning it wraps everything downstream including any new auth/enforcement middleware — an unhandled exception inside a new enforcement layer would surface as this middleware's generic 400 (`ArgumentException`) or 500 (anything else), not necessarily the clean 400 NFR3 requires for a malformed header, unless the enforcement code explicitly produces the right status itself rather than throwing.
- `Migrate()`/`AdminSeeder.Seed` run inside `CreateScope()` (`Program.cs:100-116`) **before** the HTTP pipeline is configured (`Program.cs:118` onward) — any new fail-fast `ValidateConfiguration` call for an enforcement flag would need to slot into this same pre-pipeline scope block to follow precedent, and a misconfigured flag (e.g. non-boolean value) crashing startup would affect the single production environment immediately per FR5's stated concern about no dev/staging environment.
- No `[AllowAnonymous]` attribute exists anywhere in the codebase — if global enforcement is implemented via a controller/global-level `[Authorize]`-equivalent, exempting `POST /oauth/token` will be the *first* use of an allow-anonymous-style escape hatch in this codebase, with no existing precedent to follow.
