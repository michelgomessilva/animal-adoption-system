## §2 — Execution Path

There is no existing execution path for admin identity/seeding — this is greenfield. The closest analogous path (entity creation) is:

1. `AnimalController.Create` (`back-end/ONG.API/Controllers/AnimalController.cs:22-27`) — `[HttpPost]`, binds `CreateAnimalCommand` from the request body via `[ApiController]` implicit `[FromBody]`.
2. → `CreateAnimalHandler.Handle(command)` (`back-end/ONG.Application/UseCases/Animals/CreateAnimal/CreateAnimalHandler.cs:14-33`) — constructs `new Animal(...)` from the command fields.
3. → `IAnimalRepository.Add(animal)` then `SaveChanges()` (`back-end/ONG.Infrastructure/Repositories/AnimalRepository.cs:16-19,24-27`) — `_context.Animals.Add(animal)`, `_context.SaveChanges()`.
4. → `ONGDbContext` persists via EF Core/Npgsql to the `Animals` table in Postgres.

No comparable path exists yet for provisioning a row outside of an HTTP request (i.e., a seed-on-startup or seed-via-migration mechanism) — `Program.cs` has no such logic today (confirmed above).

## §3 — Existing Patterns (reuse)

- Rich domain entity with private setters + public behavior method (`back-end/ONG.Domain/Entitites/Animal.cs:7-25`) — the only precedent for how a new entity (`Admin`) would be shaped in this codebase.
- Repository interface (`ONG.Application/Repositories/`) + EF Core implementation (`ONG.Infrastructure/Repositories/`), constructor-injecting `ONGDbContext`, explicit `SaveChanges()` on the repository (`back-end/ONG.Application/Repositories/IAnimalRepository.cs:1-11`, `back-end/ONG.Infrastructure/Repositories/AnimalRepository.cs:1-29`) — the only precedent for a repository pair.
- EF Core Migrations under `back-end/ONG.Infrastructure/Migrations/`, generated via `dotnet ef migrations add` (per CLAUDE.md commands), naming `{timestamp}_{PascalCaseName}.cs` + `.Designer.cs`, both referencing `ONGDbContextModelSnapshot.cs` — the only precedent for adding a table.
- `builder.Configuration.GetConnectionString(...)` / `IConfiguration` (`back-end/ONG.API/Program.cs:19-21`) — the only precedent for reading a secret from configuration (user-secrets locally, env var `ConnectionStrings__DefaultConnection` in Docker per `back-end/docker-compose.yml:29` and `back-end/README.md:64-70`).
- `AddScoped<IInterface, Impl>()` / `AddScoped<ConcreteHandler>()` inline registration in `Program.cs` (`back-end/ONG.API/Program.cs:26-27`) — the only precedent for DI wiring; no `AddApplication()`/`AddInfrastructure()` extension methods exist yet.

## §6 — Open Questions

- Q1 — What concrete fields does `Admin` need beyond the parent feature's stated `Id`, `Username`, `PasswordHash`, `CreatedAt` (`docs/features/F0001-admin-login.md:112-114`)? E.g. is an `UpdatedAt` or `IsActive` field needed.
- Q2 — Which password-hashing mechanism to add — parent feature spec (`docs/features/F0001-admin-login.md:123-124`) explicitly leaves this as a design-slice decision between ASP.NET Core's `PasswordHasher<T>` (no extra package, since `Microsoft.AspNetCore.Identity` itself isn't referenced but `PasswordHasher<T>` ships in a lighter package) and `BCrypt.Net` (external NuGet package, not currently referenced anywhere in the solution).
- Q3 — How is the seed mechanism implemented — options observed as *possible* in this codebase's toolchain (not decided): EF Core migration-embedded seed (`migrationBuilder.InsertData` / `HasData` in `OnModelCreating`, though `OnModelCreating` doesn't exist yet) vs. a startup-time idempotent seed check in `Program.cs` (no precedent currently exists for either — `Program.cs` has zero seeding logic today).
- Q4 — Where does the seed password come from in configuration — no `Admin`/seed-related key exists yet in `appsettings.json`, `appsettings.Development.json`, or `docker-compose.yml`'s `backend.environment` block (only `ASPNETCORE_ENVIRONMENT`, `ASPNETCORE_URLS`, `ConnectionStrings__DefaultConnection` are currently passed — `back-end/docker-compose.yml:24-27`). A new config key/env var will need to be introduced; naming/shape is a design decision.
- Q5 — Should `Admin` get its own `IAdminRepository`/`AdminRepository` pair mirroring `IAnimalRepository`/`AnimalRepository`, or does the seed mechanism talk to `ONGDbContext` directly? The existing repository pattern only has one precedent (`Animal`) and this slice explicitly has no endpoint/use-case yet (per `docs/features/F0001.1-admin-identity.md:29-35`), so there's no Handler that would obviously consume a repository this slice.
- Q6 — `ONGDbContext` currently has no `OnModelCreating` override (`back-end/ONG.Infrastructure/DataBase/ONGDbContext.cs`) — adding `Admin` may be the first entity requiring either pure convention-based mapping (matching the current `Animal` approach, which also has no Fluent config) or introduction of Fluent API/`OnModelCreating`, e.g. for a unique index on `Username`.

## §7 — Risks / Gotchas

- `ONGDbContext` has no `OnModelCreating` (`back-end/ONG.Infrastructure/DataBase/ONGDbContext.cs`) — there is currently no unique-constraint enforcement mechanism demonstrated anywhere in this codebase (e.g. for a unique `Username`), so this slice would be introducing that pattern for the first time, not reusing one.
- No config key/secret convention exists yet for anything other than `ConnectionStrings:DefaultConnection` (`back-end/ONG.API/appsettings.json` has only `Logging`/`AllowedHosts`; `docker-compose.yml`'s `backend.environment` block only has 3 keys) — introducing a seed-password config key touches both local (`dotnet user-secrets`) and Docker (`docker-compose.yml` env var) paths, and per `back-end/README.md:64` "nunca commitar credenciais" is an explicit existing rule.
- **Known repo gap** (per CLAUDE.md): `dotnet ef database update` currently fails with "the model has pending changes" because `Animal.AdoptedAt` has no corresponding migration yet. Any new migration work in this slice will surface/compound that pending-changes state — the AdoptedAt migration gap is pre-existing and out of this slice's scope, but running `dotnet ef migrations add` for `Admin` will likely also try to pick up the pending `AdoptedAt` change unless that's addressed first or scoped carefully.
- `AdoptAnimalHandler` is constructor-injected into `AnimalController` but is **not** registered in `Program.cs` DI container (`back-end/ONG.API/Program.cs:27` only registers `CreateAnimalHandler`) — evidence that DI registration in this codebase is manual and easy to miss; a new `Admin`-related handler (if introduced later, e.g. in F0001.2) would need its own explicit `AddScoped` line.
- No `.editorconfig`, no analyzers, no `TreatWarningsAsErrors` (per CLAUDE.md) — nothing will flag inconsistent naming/casing automatically (as already happened with `CreateAnimalCommand.approximateAge`).
