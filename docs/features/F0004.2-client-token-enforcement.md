## §1 — Slice Objective

Enforce the client access token (issued by `F0004.1`'s `POST /oauth/token`) on every
existing route — public catalog and admin alike — before any request reaches business
logic, per parent FR3. The token endpoint itself stays exempt (a caller cannot present a
client token before obtaining one). Enforcement is gated behind a configuration/
environment flag (`FR5`, e.g. `ClientAuth:EnforcementEnabled`), **defaulting to
disabled**, so this slice can ship to the single production environment ahead of the
front-end's token-fetch/attach changes without breaking it — flipping the flag on later
(no redeploy) is what actually activates global rejection. A malformed client-token
header (e.g. missing `Bearer ` scheme) must produce a clean `400`, never a `500` (NFR3).
This slice does not touch admin JWT auth (`F0001`/`F0002`) or revisit revocation
semantics (deferred with `FR4`).

## §3 — Design *(filled in Design, ~150–200 lines)*

> Architectural decision and the concrete changes. Resolve all open questions from the
> research notes here. No code — decisions and shapes only.

> **Pre-decided 2026-08-25 (user conversation, ahead of formal `design-slice`):**
> `ClientAuth:EnforcementEnabled` is a **two-state boolean**, not a three-state flag —
> a `ShadowMode`/log-only middle state was considered and explicitly rejected as
> unnecessary for this slice. Its semantics are scoped narrowly: the flag governs
> **only** what happens when a request carries **no client token at all**.
> - **Flag off (default):** no token → request passes through unchanged (today's
>   behavior). A token, if present, is still validated — valid passes, invalid/
>   expired/malformed is rejected (safe unconditionally, since no real caller sends a
>   client token today, so rejecting a bad one can't break existing traffic).
> - **Flag on:** no token → rejected. A present token is validated exactly as above.
>
> Rationale: this lets the front-end test the *positive* path (attach a valid client
> token, get the normal response) against production immediately after this slice
> ships, with the flag still off and zero risk to existing unauthenticated traffic —
> only the *negative* path (missing token → rejection) is gated by the flag, and that
> one is exercised locally via Docker Compose with the flag enabled there instead.

### Architectural decision

A single new pipeline middleware, **`ClientTokenEnforcementMiddleware`**
(`ONG.API/Middleware/`), registered in `Program.cs` between `UseCors` and
`UseAuthentication`. It is a pure gatekeeper — it never sets `HttpContext.User` — that
decides pass/400/401 for every request, then either calls `next()` or short-circuits
the response itself (mirrors `ExceptionHandlingMiddleware`'s `RequestDelegate _next` /
`InvokeAsync(HttpContext)` shape, the only existing middleware precedent).

**Why middleware, not a second `AddJwtBearer` scheme / `AddPolicyScheme`:** the flag's
asymmetric semantics ("missing token conditionally allowed, present token *always*
validated") don't map onto a standard authentication-scheme/`[Authorize]` policy,
which is a uniform reject/allow gate. Expressing the flag branch would still require
custom code running *before* authentication either way. A second scheme + policy
forwarding adds two DI registrations and scheme-selection logic for a single exempt
route today, for no behavioral gain over one middleware.

**Why global middleware, not per-action `[Authorize(AuthenticationSchemes = ...)]`:**
the repo has zero `[AllowAnonymous]`/global-policy precedent; annotating every action
across `AnimalController`/`OAuthController`/`AuthController` is a larger diff and,
more importantly, is opt-in — a new controller/action added later would default to
*unprotected* unless someone remembers the attribute. Global middleware with one
exemption is opt-out, the safer default.

**Why a hardcoded path check for the `/oauth/token` exemption, not `[AllowAnonymous]`
+ endpoint-metadata inspection:** `[AllowAnonymous]` would be the idiomatic ASP.NET
Core answer, but reading `context.GetEndpoint()` correctly depends on where endpoint
routing has been inserted in the pipeline — this app never calls `UseRouting()`
explicitly, relying on the framework's implicit insertion, which is not something to
build a security exemption on top of without a dedicated verification pass. A
hardcoded `Path`+`Method` check for the one route that needs it is simpler, has no
ordering dependency, and is exactly as correct. Revisit if a second exempt route is
ever needed.

**Why a dedicated `IClientTokenValidator` (Application interface) /
`ClientTokenValidator` (Infrastructure impl) instead of validating the JWT inline in
the middleware:** mirrors the existing `ITokenGenerator`/`JwtTokenGenerator` split and
the repo-wide "interface in Application, implementation in Infrastructure" convention
(used for repositories today). Keeps HTTP/status-code concerns in the API-layer
middleware and JWT/crypto mechanics (reading `Jwt:Key`, building
`TokenValidationParameters`) in Infrastructure, rather than duplicating what
`Program.cs`'s existing `AddJwtBearer` setup already does for the admin scheme.

### Changes by layer

- **API (`ONG.API`)**
  - New `Middleware/ClientTokenEnforcementMiddleware.cs` — `InvokeAsync(HttpContext)`,
    constructor-injects `IClientTokenValidator` and `IOptions<ClientAuthOptions>`.
  - New `Middleware/ClientAuthOptions.cs` — `{ bool EnforcementEnabled }`, bound via
    `builder.Services.Configure<ClientAuthOptions>(builder.Configuration.GetSection("ClientAuth"))`
    (mirrors the existing `Configure<PasswordHasherOptions>` call).
  - `Program.cs` — register the options binding, `AddScoped<IClientTokenValidator, ClientTokenValidator>()`
    (matches the `AddScoped` convention used for `ITokenGenerator`/`IClientCredentialsProvider`,
    even though the validator is stateless), `app.UseMiddleware<ClientTokenEnforcementMiddleware>()`
    inserted after `app.UseCors(OpenCorsPolicy)` and before `app.UseAuthentication()`. Inside
    the existing `CreateScope()` block (alongside the other two `ValidateConfiguration`
    calls), eagerly resolve `scope.ServiceProvider.GetRequiredService<IOptions<ClientAuthOptions>>().Value`
    once — this forces a bind-time error (e.g. a non-boolean env-var value) to crash at
    startup rather than lazily on the first request, consistent with the existing
    fail-fast precedent. No bespoke `ValidateConfiguration` method is needed: the only
    thing to validate is "does this parse as a bool," which `IOptions<T>` binding already
    enforces by throwing on first access.
  - No controller files change. `AnimalController`'s `List` action's
    `HttpContext.User.Identity?.IsAuthenticated` check is unaffected — the new
    middleware never touches `HttpContext.User`, so it continues to reflect only the
    admin JWT scheme, exactly as today (resolves research §7's risk about this line's
    meaning shifting).
- **Infrastructure (`ONG.Infrastructure`)**
  - New `Security/ClientTokenValidator.cs` implementing `IClientTokenValidator`.
    Constructor-injects `IConfiguration`. `Validate(string token)` returns a
    `ClientTokenValidationStatus` enum (`StructurallyInvalid` / `SemanticallyInvalid` /
    `Valid`): uses `JwtSecurityTokenHandler.CanReadToken(token)` first (false →
    `StructurallyInvalid`), then `ValidateToken` with `TokenValidationParameters`
    pinned to `ValidIssuer = JwtTokenGenerator.ClientTokenIssuer`,
    `IssuerSigningKey` from `Jwt:Key`, `ValidateLifetime = true` — catching
    `SecurityTokenException` (covers expired / bad signature / wrong issuer) →
    `SemanticallyInvalid`; success → `Valid`.
  - `Security/JwtTokenGenerator.cs` — widen `ClientTokenIssuer` from `private const`
    to `internal const` (same file/namespace assembly, `ONG.Infrastructure.Security`)
    so `ClientTokenValidator` references the exact same issuer string instead of a
    duplicated magic value. No other change to `JwtTokenGenerator`.
- **Application (`ONG.Application`)**
  - New `Security/IClientTokenValidator.cs` — `ClientTokenValidationStatus Validate(string token)`.
    Same folder as the existing `ITokenGenerator`/`IClientCredentialsProvider`.
- **Domain (`ONG.Domain`)** — no change.
- **Config** — new `appsettings.json` section `"ClientAuth": { "EnforcementEnabled": false }`
  (safe default, mirrors FR5). Delivered via the existing double-underscore env-var
  convention as `ClientAuth__EnforcementEnabled`, but — unlike `Jwt:Key`/
  `ClientCredentials:*` — **not** wired through `docker-compose.yml`'s `${VAR:?message}`
  required-fail syntax, since a missing value has a safe, intentional default (disabled)
  rather than being a startup-blocking secret. `docker-compose.yml` passes it through as
  an optional override (default `false` if unset); `.env.example` documents it as
  optional. Render/CI wiring follows the same "optional, defaults off" shape — exact
  file edits are a `plan-slice` concern, not re-derived here (per research §8, the
  *pattern* for wiring any new key is already documented in `CLAUDE.md`).

### Resolved open questions

- **Q1** (how to validate a client token given the single admin-pinned `AddJwtBearer`
  scheme) → custom middleware performing manual `JwtSecurityTokenHandler` validation
  via the new `IClientTokenValidator`, not a second auth scheme. See "Architectural
  decision" above.
- **Q2** (where the `ClientAuth:EnforcementEnabled` flag is read) → bound as
  `ClientAuthOptions` via `Configure<T>` (mirrors `PasswordHasherOptions`), consumed
  as constructor-injected `IOptions<ClientAuthOptions>` in the middleware; eagerly
  resolved once at startup inside the existing `CreateScope()` block to fail fast on
  a bind error.
- **Q3** (how `POST /oauth/token` is exempted) → hardcoded `Path`+`Method` check at
  the top of the middleware, not `[AllowAnonymous]`. See rationale above.
- **Q4** (what produces the required 400 for a malformed header vs. today's 401 for
  an unparsable token value) → the middleware itself computes the status, never
  throws: missing `Authorization` header = "no token" (flag-gated, not malformed); a
  present header that isn't a well-formed `Bearer <token>` (parse failure, wrong
  scheme, empty token value) or a token string that isn't structurally a JWT
  (`CanReadToken` false) = `400`; a structurally-valid JWT that fails semantic
  validation (bad signature/issuer/expired) = `401`. This is intentionally a
  *narrower* malformed-vs-invalid split than the existing admin `AddJwtBearer`
  handler's behavior (which returns 401 for any unparsable token) — the two schemes
  are independent and this slice does not change the admin scheme's behavior.
- **Q5** (per-route `[Authorize]` vs. blanket middleware) → blanket middleware with
  one exemption. See "Architectural decision" above.
- **Q6** (interaction with CORS preflight) → no special-casing needed: the middleware
  is registered *after* `UseCors`, and ASP.NET Core's CORS middleware already
  short-circuits a matched preflight `OPTIONS` request before calling `next()` — the
  same ordering `CorsPolicyTests.cs` already exercises against the admin-protected
  routes today. Resolution is verified by extending that test file with an
  enforcement-flag-on case (§4), not by writing new preflight-handling code.
- **Q7** (exact config key/shape) → `ClientAuth:EnforcementEnabled` (bool), confirmed
  by the pre-decision note above; no other keys needed for this slice.

> **Design revision 2026-08-25 (post-implementation, user conversation):** implementing
> Task 4 as originally designed above (client token read from the `Authorization` header)
> broke every existing admin-authenticated E2E test (`AnimalControllerAuthTests`, 10
> failures) — admin routes send the admin JWT in `Authorization`, and the middleware
> correctly rejected it as an invalid *client* token, regardless of the enforcement flag.
> The root issue: FR3/the parent spec's acceptance criteria ("layering with admin auth")
> require a client token **and** an admin JWT to be validated **independently** on the
> same request for admin-only routes — two distinct credentials that cannot both fit in
> one `Authorization` header.
>
> **Resolution:** the client token is read from a new dedicated request header,
> **`X-Client-Token: <token>`**, instead of `Authorization`. `Authorization` remains
> exclusively for the admin JWT (`AddJwtBearer`/`[Authorize]`), completely unchanged.
> This mirrors the industry-standard pattern for combining an app-level credential with a
> user-level bearer token on the same request (e.g. AWS API Gateway's `x-api-key` +
> `Authorization`, Apigee/Kong's API-key header + bearer auth) — not a workaround specific
> to this codebase.
>
> Every place in §3/§4/§5 above that reads "`Authorization: Bearer <client token>`" for
> **client-token** validation purposes is superseded: read `X-Client-Token: <token>`
> instead (no `Bearer ` scheme prefix needed, since the header is single-purpose — its
> presence alone conveys intent). The "malformed header" cases (NFR3) now mean: header
> present but empty/whitespace, or its value doesn't parse as a JWT (`CanReadToken`
> false) → `400`. Test cases and helper code in §4/§5 that mint/attach a token via
> `Authorization: Bearer <client token>` should instead set the `X-Client-Token` header
> directly; tests that send an **admin** token via `Authorization` are unaffected. One
> test should be added beyond the original list: valid `X-Client-Token` **and** valid
> admin `Authorization` bearer together on `POST /api/animals` → `201` — the actual
> production "layered" scenario that the original design never exercised.

> provider, which is the standard, documented fix for "scoped service in middleware."

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Text;
using Microsoft.Extensions.Configuration;
using Microsoft.IdentityModel.Tokens;
using ONG.Application.Security;

namespace ONG.Infrastructure.Security
{
    public class ClientTokenValidator : IClientTokenValidator
    {
        private readonly IConfiguration _configuration;

        public ClientTokenValidator(IConfiguration configuration)
        {
            _configuration = configuration;
        }

        public ClientTokenValidationStatus Validate(string token)
        {
            var handler = new JwtSecurityTokenHandler();

            if (!handler.CanReadToken(token))
            {
                return ClientTokenValidationStatus.StructurallyInvalid;
            }

            var key = _configuration["Jwt:Key"]!;
            var validationParameters = new TokenValidationParameters
            {
                ValidateIssuer = true,
                ValidIssuer = JwtTokenGenerator.ClientTokenIssuer,
                ValidateAudience = false,
                ValidateLifetime = true,
                ValidateIssuerSigningKey = true,
                IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(key))
            };

            try
            {
                handler.ValidateToken(token, validationParameters, out _);
                return ClientTokenValidationStatus.Valid;
            }
            catch (SecurityTokenException)
            {
                return ClientTokenValidationStatus.SemanticallyInvalid;
            }
        }
    }
}
```

```csharp
using System;
using System.Net.Http.Headers;
using System.Threading.Tasks;
using Microsoft.AspNetCore.Http;
using Microsoft.Extensions.Options;
using ONG.Application.Security;

namespace ONG.API.Middleware
{
    public class ClientTokenEnforcementMiddleware
    {
        private const string ExemptPath = "/oauth/token";

        private readonly RequestDelegate _next;
        private readonly ClientAuthOptions _options;

        public ClientTokenEnforcementMiddleware(RequestDelegate next, IOptions<ClientAuthOptions> options)
        {
            _next = next;
            _options = options.Value;
        }

        public async Task InvokeAsync(HttpContext context, IClientTokenValidator validator)
        {
            if (HttpMethods.IsPost(context.Request.Method)
                && string.Equals(context.Request.Path.Value, ExemptPath, StringComparison.OrdinalIgnoreCase))
            {
                await _next(context);
                return;
            }

            var authHeader = context.Request.Headers.Authorization.ToString();

            if (string.IsNullOrEmpty(authHeader))
            {
                if (_options.EnforcementEnabled)
                {
                    await WriteStatus(context, StatusCodes.Status401Unauthorized, "Missing client access token.");
                    return;
                }

                await _next(context);
                return;
            }

            if (!AuthenticationHeaderValue.TryParse(authHeader, out var parsedHeader)
                || !string.Equals(parsedHeader.Scheme, "Bearer", StringComparison.Ordinal)
                || string.IsNullOrWhiteSpace(parsedHeader.Parameter))
            {
                await WriteStatus(context, StatusCodes.Status400BadRequest, "Malformed Authorization header.");
                return;
            }

            switch (validator.Validate(parsedHeader.Parameter))
            {
                case ClientTokenValidationStatus.StructurallyInvalid:
                    await WriteStatus(context, StatusCodes.Status400BadRequest, "Malformed client access token.");
                    return;
                case ClientTokenValidationStatus.SemanticallyInvalid:
                    await WriteStatus(context, StatusCodes.Status401Unauthorized, "Invalid or expired client access token.");
                    return;
            }

            await _next(context);
        }

        private static async Task WriteStatus(HttpContext context, int statusCode, string message)
        {
            context.Response.StatusCode = statusCode;
            await context.Response.WriteAsJsonAsync(new { message });
        }
    }
}
```
