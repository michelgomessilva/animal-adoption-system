## §1 — Slice Objective

Add `GET /api/animals`, the first read endpoint on the `Animal` aggregate: a new
`IAnimalRepository` read method, a `ListAnimalsCommand`/`ListAnimalsHandler` pair
following the existing Command+Handler shape, and a thin controller action that
branches on `HttpContext.User.Identity?.IsAuthenticated` (populated by the JWT
bearer scheme already wired in `F0002.1`) to return only `Status == Available`
animals to anonymous or bad-token callers, and every animal to an authenticated
admin. No query-string filters yet (`F0003.2`) — this slice is the smallest
end-to-end useful increment: the endpoint exists, is publicly reachable (no
`401` on missing/invalid token per FR4), and enforces the visibility rule
correctly per FR1–FR4 of the parent spec.

## §3 — Design

> Architectural decision and the concrete changes. Resolve all open questions from the
> research notes here. No code — decisions and shapes only.

### Architectural decision

Extend the existing Command+Handler pattern with a new read-only slice:
`IAnimalRepository.GetAll()` (sync, no parameters, mirrors `Add`/`SaveChanges`'s
synchronicity) → `ListAnimalsCommand` (one property, `IsAuthenticated`, built by
the controller from `HttpContext.User` — not model-bound, unlike
`CreateAnimalCommand`) → `ListAnimalsHandler.Handle(command)`, which fetches
every animal via the repository and applies the visibility rule
(`Status == Available`) in-memory when the caller isn't authenticated. The
visibility rule is a use-case-level concern — it depends on caller identity,
which `Animal` has no knowledge of — so it stays in the Handler, exactly like
`CreateAnimalHandler`'s own enum-validation guard clauses stay there rather
than on `Animal`. The controller stays thin: read `IsAuthenticated`, build the
command, call the handler, return `Ok(...)`. No `[Authorize]` on the new
action — `UseAuthentication` already runs unconditionally ahead of
`MapControllers` (`Program.cs:108`), so a valid bearer token still populates
`HttpContext.User` with no `[Authorize]` present; only `[Authorize]` turns a
missing/invalid token into a `401` challenge, and omitting it is what makes
FR4 ("bad token doesn't 401") work for free from existing middleware — no new
auth mechanism.

**Rejected alternative — filter in the repository** (e.g.
`GetAll(bool includeAll)` or a `GetAvailable()`/`GetAll()` pair): would leak an
auth/business decision (which animals a caller may see) into the data-access
layer, which today is intentionally free of business logic (`Add`/
`SaveChanges` are pure passthroughs). The in-memory filter keeps that boundary
intact and costs nothing at NFR2's stated small-dataset scale.

**Rejected alternative — make `GetAll` async** (`Task<List<Animal>>`): would
introduce the codebase's first async data-access call as a side effect of one
read endpoint. Kept sync to match `Add`/`SaveChanges`'s existing convention;
revisit deliberately, project-wide, if performance ever requires it.

### Changes by layer

- **`ONG.Domain`** — no changes. `Animal`'s constructor bug (never assigns
  `Species`, research §7) is a real, separate defect, out of this slice's
  scope — fixing it here would mix an unrelated bug fix into a read-endpoint
  PR. See "Resolved open questions" (Q3) for the follow-up recommendation.
- **`ONG.Application`**:
  - `IAnimalRepository`: add `List<Animal> GetAll();`.
  - New `UseCases/Animals/ListAnimals/ListAnimalsCommand.cs`: plain class,
    `public bool IsAuthenticated { get; set; }`. No `DataAnnotations` — this
    isn't user input; the controller builds it directly from
    `HttpContext.User`. The GET action has no request body or query string in
    this slice.
  - New `UseCases/Animals/ListAnimals/ListAnimalsHandler.cs`:
    constructor-injects `IAnimalRepository`; `Handle(ListAnimalsCommand
    command)` returns `List<Animal>` — calls `_repository.GetAll()`, then
    `command.IsAuthenticated ? animals : animals.Where(a => a.Status ==
    Status.Available).ToList()`.
- **`ONG.Infrastructure`** — `AnimalRepository.GetAll()`: `return
  _context.Animals.ToList();` (no `Include`s — `Animal` has no navigation
  properties).
- **`ONG.API`**:
  - `AnimalController`: second constructor-injected dependency
    `ListAnimalsHandler`; new action `[HttpGet] public IActionResult List()`
    — no `[Authorize]`. Reads `HttpContext.User.Identity?.IsAuthenticated ??
    false`, builds `ListAnimalsCommand`, calls the handler, returns
    `Ok(animals)`.
  - `Program.cs`: `builder.Services.AddScoped<ListAnimalsHandler>();` next to
    the existing `AddScoped<CreateAnimalHandler>()` (`Program.cs:53`) — same
    registration shape (concrete type, no interface). No change to
    `AddAuthentication`/`AddJwtBearer`/pipeline order — reused as-is.

### Migrations

None — read-only, existing `Animals` table/columns, no new index (per
research §7, acceptable at NFR2's stated MVP scale; revisit if a real dataset
shows a full-scan cost becomes a problem).

### Explicit reuse

- Command+Handler shape (research §3) — `ListAnimalsCommand`/
  `ListAnimalsHandler`, one folder under `UseCases/Animals/ListAnimals/`,
  handler registered by concrete type in `Program.cs`, called directly from
  the controller (no mediator).
- Repository interface/impl split (research §3) — `IAnimalRepository`/
  `AnimalRepository`, same constructor-injection of `ONGDbContext`.
- No-DTO convention (research §3, NFR1) — action returns `List<Animal>`
  directly via `Ok(...)`, same shape as `Create`'s `StatusCode(201, animal)`.
- `LoginApiFactory` + existing E2E fixture (research §3) — this slice's E2E
  tests are added as new `[Fact]`s inside `AnimalControllerAuthTests.cs`,
  reusing its already-private `GetValidTokenAsync()`, `MintExpiredToken()`,
  `TamperToken()`, and `_client` exactly as-is — no extraction, no new test
  class.
- Fake-repository unit-test pattern (`LoginHandlerTests.FakeAdminRepository`)
  — `ListAnimalsHandlerTests` uses a private nested `FakeAnimalRepository :
  IAnimalRepository` seeded with a fixed `List<Animal>`, mirroring
  `FakeAdminRepository`'s shape exactly.

### Resolved open questions

- **Q1 (repository shape)** → `GetAll()` with no parameters, returning every
  animal; visibility filtering happens in `ListAnimalsHandler`, not the
  repository — keeps the repository free of business logic (see rejected
  alternative above).
- **Q2 (async vs sync)** → sync (`List<Animal> GetAll()`), matching `Add`/
  `SaveChanges`'s existing convention; the first async data-access call is
  out of scope for this slice.
- **Q3 (response shape)** → raw `List<Animal>` via `Ok(...)`, no new DTO, per
  NFR1 — no field needs hiding from anonymous callers today. The pre-existing
  `Animal.Species` constructor bug (never assigns `Species`) will surface as
  `"None"` for every animal once this endpoint ships; this slice does **not**
  fix it (unrelated defect — fixing it here would mix an unrelated bug fix
  into a read-endpoint PR). **Recommended follow-up:** file a dedicated
  hotfix (`/new-hotfix-spec`) for the `Animal` constructor bug once this
  slice ships.
- **Q4 (passing auth state to the Handler)** → controller reads
  `HttpContext.User.Identity?.IsAuthenticated ?? false` directly and sets it
  on `ListAnimalsCommand.IsAuthenticated`; no new abstraction needed.
- **Q5 (`[Authorize]` vs alternative)** → no `[Authorize]` on the new action
  (see architectural decision above — `UseAuthentication` already runs
  unconditionally, so omitting `[Authorize]` is what delivers FR4 with zero
  new auth plumbing).
- **Q6 (E2E test placement)** → new `[Fact]`s added directly to
  `AnimalControllerAuthTests.cs`, reusing its existing fixture and token
  helpers in place — no new test class, no extraction.

using ONG.Domain.Entitites;

namespace ONG.Application.UseCases.Animals.ListAnimals
{
    public class ListAnimalsHandler
    {

        public ListAnimalsHandler(IAnimalRepository repository)

> Note — shared-fixture ordering risk: `LoginApiFactory` gives each test
> *class instance* a fresh `Guid`-named InMemory database (`_dbName`), but

> does not guarantee declaration order across `[Fact]`s in a class. A hard
> `Assert.Empty(animals)` in `List_EmptyCatalogNoToken_Returns200WithEmptyList`
> would therefore be flaky if a sibling test happens to run first and seeds
> an animal. This is a pre-existing property of the shared fixture (not
> introduced by this slice) — the decision below works around it rather than
> fixing the fixture, which is out of scope here.
>
> **Decision:** assert only `HttpStatusCode.OK` and that the body is a JSON
> array (`body.ValueKind == JsonValueKind.Array`) in this one test — not a
> hard `Assert.Empty`. This still proves the parent AC's actual requirement
> ("empty catalog returns `200` with an array body, not `404`/`500`") without
> depending on execution order. Use this assertion body for the test instead
> of `Assert.Empty(...)`:
>
> ```csharp
> Assert.Equal(HttpStatusCode.OK, response.StatusCode);
> Assert.Equal(JsonValueKind.Array, body.ValueKind);
> ```
