## §1 — Slice Objective

Standardize every error response `ONG.API` returns — unhandled exceptions (`ExceptionHandlingMiddleware`), client-token enforcement failures (`ClientTokenEnforcementMiddleware`), invalid-credential responses (`AuthController.Login`, `OAuthController.Token`), and not-found lookups (`AnimalController.GetById`/`Update`) — on RFC 9457 `ProblemDetails`, using ASP.NET Core's built-in support. This is the feature's single slice (see parent §6 for why it isn't split further): one coherent, shippable pass over all four divergent error shapes at once.

## §3 — Design *(filled in Design, ~150–200 lines)*

> Architectural decision and the concrete changes. Resolve all open questions from the
> research notes here. No code — decisions and shapes only.

- **Architectural decision:** Use ASP.NET Core's built-in `ProblemDetails` support end to
  end, with **one global customization point** instead of four independent
  constructions. `Program.cs` calls `AddProblemDetails(options => options.CustomizeProblemDetails = ctx => { ... })`
  once; that callback runs for *every* `ProblemDetails` instance produced anywhere in the
  app — whether built manually via `IProblemDetailsService.WriteAsync` (middleware) or via
  `ControllerBase.Problem(...)` (controllers) — confirmed against the official ASP.NET
  Core docs (`error-handling.md`: "CustomizeProblemDetails... apply global customizations
  to all auto-generated problem details"). This is what satisfies NFR3 ("one documented
  pattern, not two"): the two call-site shapes differ only in *how* a `ProblemDetails` is
  handed off (service call vs. controller helper), not in how `Type`/`Instance` get
  populated — that part is centralized. No new NuGet package, no new options class, no
  new config keys (confirmed by research §4/§8) — `AddProblemDetails()`'s lambda is
  inline code, not an `IConfiguration`-bound section, so the existing `IOptions<T>`
  binding precedent (`ClientAuthOptions`) doesn't apply here and isn't needed.
  **Alternative rejected:** giving each of the 4 call sites its own hand-rolled
  `ProblemDetails` construction (status quo pattern, just swapping the anonymous
  `{ message }` object for a `ProblemDetails` object) — rejected because it would leave
  `Type`/`Instance` either omitted or reimplemented 4 times, reproducing the exact
  inconsistency this feature exists to remove.

- **Changes by layer** (single-project change, `ONG.API` only — no `Application`/
  `Domain`/`Infrastructure` changes, confirmed by research §4):
  - **Composition root** (`Program.cs`, near existing `AddControllers()` at L39–44) —
    add `builder.Services.AddProblemDetails(options => { options.CustomizeProblemDetails = ctx => { ctx.ProblemDetails.Instance = ctx.HttpContext.Request.Path; ctx.ProblemDetails.Type ??= $"https://httpstatuses.io/{ctx.ProblemDetails.Status}"; }; });`.
    Pure service registration — no pipeline reordering (resolves **Q7**: `AddProblemDetails()`
    is DI-only, so it is unaffected by `UseSwagger`/`UseSwaggerUI` running before
    `ExceptionHandlingMiddleware`, confirmed against docs).
  - **`ExceptionHandlingMiddleware`** — add `IProblemDetailsService` as an extra
    `InvokeAsync(HttpContext, IProblemDetailsService)` parameter (method injection, not
    constructor injection — this is conventional middleware, constructed once at
    startup, so per-request-safe services must be method-injected, matching how ASP.NET
    Core's own middleware samples resolve `IProblemDetailsService`). Both catch blocks
    set `context.Response.StatusCode` explicitly (as today) then call
    `problemDetailsService.WriteAsync(new ProblemDetailsContext { HttpContext = context, ProblemDetails = new ProblemDetails { Status = <code>, Title = <title>, Detail = <detail> } })`
    instead of `WriteAsJsonAsync(new { message })`. 400 case: `Detail = ex.Message` (same
    info as today, just relocated to `Detail`). 500 case: `Detail` stays the existing
    fixed generic string — **never** `ex.Message` (NFR2/FR2, preserves the one thing this
    file already gets right per research §7). The `catch (Exception)` block keeps its
    unused/unnamed exception variable — no logging added, out of this slice's scope.
  - **`ClientTokenEnforcementMiddleware`** — same method-injection shape added to
    `InvokeAsync`. The private `WriteStatus(HttpContext, int, string)` helper is replaced
    by a same-shaped private helper that takes `(HttpContext, IProblemDetailsService, int status, string title, string detail)`
    and calls `WriteAsync` the same way as above — keeping the "one helper per
    middleware" precedent (research §3) rather than introducing a shared cross-file
    helper (no third file needs this shape, so extracting one now would be premature
    abstraction). All 3 call sites (missing token, `StructurallyInvalid`,
    `SemanticallyInvalid`) route through it with the same status codes as today (401,
    400, 401) — **NFR1: no status-code changes**, body only.
  - **`AuthController.Login` / `OAuthController.Token`** — `Unauthorized(new { message = "..." })`
    becomes `Problem(statusCode: StatusCodes.Status401Unauthorized, title: "Invalid credentials.", detail: "Invalid username or password.")`
    (Auth) / `detail: "Invalid client_id or client_secret."` (OAuth) — **resolves Q3**:
    reuse the exact current strings verbatim as `Detail`, don't invent new copy (least
    surprising, and the front-end's `parseValidationBody` fallback already reads `title`
    if `message` is absent, so no front-end coordination is needed either way — confirmed
    in parent spec).
  - **`AnimalController.GetById` / `Update`** — bare `NotFound()` becomes
    `Problem(statusCode: StatusCodes.Status404NotFound, title: "Animal not found.", detail: $"No animal found with id '{id}'.")`
    — **resolves Q4**. Uses `Problem(...)` (not `NotFound(ProblemDetails)`) for the same
    reason as the two controllers above: one controller-side helper, not two. The
    existing `[ProducesResponseType]` annotations on `GetById` (`AnimalController.cs:52-54`)
    are updated to declare `typeof(ProblemDetails)` for the 400/404 entries — **resolves
    Q6** (accurate Swagger/OpenAPI generation; low-cost, already-present attribute, no
    reason to leave it lying about the actual response type).
  - No domain/service/persistence layer changes — this is purely how `ONG.API` shapes a
    response it was already going to send.

- **Migrations:** none (no schema/entity touched, confirmed research §4/DB Impact).

- **Explicit reuse:**
  - `[ApiController]` on all three controllers → unlocks `ControllerBase.Problem(...)`,
    already present, never used until now (research §3).
  - Existing middleware shape (`RequestDelegate next` ctor, `InvokeAsync(HttpContext, ...)`
    method, private `Write*`-style helper) — reused as-is, only the helper's *body*
    changes from `WriteAsJsonAsync(new { message })` to `IProblemDetailsService.WriteAsync(...)`.
  - Existing E2E test infrastructure (`WebApplicationFactory<Program>`,
    `ReadFromJsonAsync<JsonElement>()` + `GetProperty(...)`) — reused unchanged; only the
    property names asserted change (`message` → `title`/`detail`).
  - No new `IOptions<T>`-bound options class — deliberately *not* reusing the
    `ClientAuthOptions` precedent, since `CustomizeProblemDetails` needs no
    `IConfiguration` section (research §3 flagged this precedent as available, but it
    doesn't fit here).

- **Resolved open questions** (research §6):
  - **Q1** — `instance` = `HttpContext.Request.Path`, set once in the global
    `CustomizeProblemDetails` callback (not per call site). `type` defaults to the
    RFC 9457-conventional `https://httpstatuses.io/{status}` when not already set,
    also set globally.
  - **Q2** — Middleware constructs `ProblemDetails` via `IProblemDetailsService.WriteAsync`
    (method-injected into `InvokeAsync`), per the official docs' documented pattern for
    "Problem details from middleware." Not `Results.Problem(...)` (a minimal-API/endpoint
    result type, awkward to invoke from raw middleware) and not a manually
    `JsonSerializer`-serialized `ProblemDetails` (would bypass `CustomizeProblemDetails`
    entirely, reintroducing the inconsistency this design centralizes away).
  - **Q3** — `Problem(statusCode: 401, title: "Invalid credentials.", detail: <existing message verbatim>)`
    in both `AuthController` and `OAuthController`.
  - **Q4** — `Problem(statusCode: 404, title: "Animal not found.", detail: $"No animal found with id '{id}'.")`
    in both `AnimalController.GetById` and `Update`.
  - **Q5** — All 9 existing tests that assert the `message` property are updated in this
    slice to assert `detail` (and, where the test's intent is exercising the *shape* not
    just the value, `title`) instead. The 6 status-code-only tests are left as-is unless
    naturally superseded by a new/updated test in §4 below — they still pass unchanged
    since status codes don't move (NFR1).
  - **Q6** — Yes, `[ProducesResponseType(typeof(ProblemDetails), StatusCodes.Status400BadRequest)]` /
    `...Status404NotFound)]` added to `AnimalController.GetById` alongside its existing
    200 entry.
  - **Q7** — No pipeline-ordering impact; `AddProblemDetails()` is a service
    registration, confirmed against docs (see architectural decision above).

```csharp
using Microsoft.AspNetCore.Mvc;

namespace ONG.API.Middleware
{
    public class ExceptionHandlingMiddleware
    {
        private readonly RequestDelegate _next;

        public ExceptionHandlingMiddleware(RequestDelegate next)
        {
            _next = next;
        }

        public async Task InvokeAsync(HttpContext context, IProblemDetailsService problemDetailsService)
        {
            try
            {
                await _next(context);
            }
            catch (ArgumentException ex)
            {
                context.Response.StatusCode = StatusCodes.Status400BadRequest;

                await problemDetailsService.WriteAsync(new ProblemDetailsContext
                {
                    HttpContext = context,
                    ProblemDetails = new ProblemDetails
                    {
                        Status = StatusCodes.Status400BadRequest,
                        Title = "Invalid request.",
                        Detail = ex.Message
                    }
                });
            }
            catch (Exception)
            {
                context.Response.StatusCode = StatusCodes.Status500InternalServerError;

                await problemDetailsService.WriteAsync(new ProblemDetailsContext
                {
                    HttpContext = context,
                    ProblemDetails = new ProblemDetails
                    {
                        Status = StatusCodes.Status500InternalServerError,
                        Title = "An unexpected error occurred.",
                        Detail = "An unexpected error occurred."
                    }
                });
            }
        }
    }
}
```

```csharp
    public class ClientTokenEnforcementMiddleware
    {
        private const string ExemptPath = "/oauth/token";
        private const string ClientTokenHeaderName = "X-Client-Token";

        private readonly RequestDelegate _next;
        private readonly ClientAuthOptions _options;

        public ClientTokenEnforcementMiddleware(RequestDelegate next, IOptions<ClientAuthOptions> options)
        {
            _next = next;
            _options = options.Value;
        }

        public async Task InvokeAsync(HttpContext context, IClientTokenValidator validator, IProblemDetailsService problemDetailsService)
        {
            if (HttpMethods.IsPost(context.Request.Method)
                && string.Equals(context.Request.Path.Value, ExemptPath, StringComparison.OrdinalIgnoreCase))
            {
                await _next(context);
                return;
            }

            var clientToken = context.Request.Headers[ClientTokenHeaderName].ToString();

            if (string.IsNullOrEmpty(clientToken))
            {
                if (_options.EnforcementEnabled)
                {
                    await WriteStatus(context, problemDetailsService, StatusCodes.Status401Unauthorized, "Missing client access token.", "Missing client access token.");
                    return;
                }

                await _next(context);
                return;
            }

            switch (validator.Validate(clientToken))
            {
                case ClientTokenValidationStatus.StructurallyInvalid:
                    await WriteStatus(context, problemDetailsService, StatusCodes.Status400BadRequest, "Malformed client access token.", "Malformed client access token.");
                    return;
                case ClientTokenValidationStatus.SemanticallyInvalid:
                    await WriteStatus(context, problemDetailsService, StatusCodes.Status401Unauthorized, "Invalid or expired client access token.", "Invalid or expired client access token.");
                    return;
            }

            await _next(context);
        }

        private static async Task WriteStatus(HttpContext context, IProblemDetailsService problemDetailsService, int statusCode, string title, string detail)
        {
            context.Response.StatusCode = statusCode;

            await problemDetailsService.WriteAsync(new ProblemDetailsContext
            {
                HttpContext = context,
                ProblemDetails = new ProblemDetails
                {
                    Status = statusCode,
                    Title = title,
                    Detail = detail
                }
            });
        }
    }
}
```
