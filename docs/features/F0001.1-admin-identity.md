## §1 — Slice Objective

Introduce the `Admin` identity into the system: a new domain entity, an EF Core migration
creating its table, and a seed mechanism that provisions the single administrative user
with a securely hashed password sourced from configuration (no plaintext committed, no
signup endpoint). This slice lands the data layer only — no `POST /auth/login` endpoint
yet (that is `F0001.2`) — but is independently shippable and reviewable: after this PR,
the `Admin` row exists and can be verified in the database, with no behavior change
exposed via the API.

## §3 — Design

- **Architectural decision:** Land the `Admin` identity purely in the persistence layer,
  reusing the existing `Animal` shape (rich entity, private setters, single public ctor)
  and the existing repository/DI conventions where they genuinely apply. No `IAdminRepository`
  is introduced in this slice (see Q5) — the seed mechanism is startup/infra plumbing, not a
  use case, so it talks to `ONGDbContext` directly, the same way `Program.cs` already talks to
  configuration directly. The password is hashed with ASP.NET Core's `PasswordHasher<T>`
  (package `Microsoft.Extensions.Identity.Core`) rather than adding BCrypt.Net, because it
  ships as a small, dependency-light package (crypto + logging/options abstractions only, no
  EF-based Identity, no Identity UI), is already the ecosystem-idiomatic choice for a .NET API,
  and needs no new external service or native binding. Rejected: full
  `Microsoft.AspNetCore.Identity` (far more than a single seeded admin needs — user manager,
  roles, stores); BCrypt.Net (a new external dependency for no capability `PasswordHasher<T>`
  lacks here).

- **Changes by layer:**
  - **Domain (`ONG.Domain`)** — new `back-end/ONG.Domain/Entitites/Admin.cs`: `Id` (`Guid`),
    `Username` (`string`), `PasswordHash` (`string`), `CreatedAt` (`DateTime`), all
    `private set`, one public ctor `Admin(string username, string passwordHash)` that sets
    `Id = Guid.NewGuid()` and `CreatedAt = DateTime.UtcNow` — mirrors `Animal`'s shape exactly.
    Two behavior methods, mirroring `Animal.Adopt()`: `Rename(string newUsername)` and
    `RotatePassword(string newPasswordHash)`, each mutating exactly one private-set field —
    these exist so `AdminSeeder`'s reconcile logic (below) never needs an open setter.
    Credential *verification* (comparing a login attempt to the hash) still belongs to
    `F0001.2`, which is the first consumer that needs it.
  - **Infrastructure (`ONG.Infrastructure`)** —
    - `ONGDbContext`: add `DbSet<Admin> Admins { get; set; }` and a new
      `OnModelCreating(ModelBuilder modelBuilder)` override — the first one in this context —
      configuring `modelBuilder.Entity<Admin>().HasIndex(a => a.Username).IsUnique();` (Q6).
    - New `back-end/ONG.Infrastructure/DataBase/AdminSeeder.cs`: static method
      `Seed(ONGDbContext context, IConfiguration configuration)`, now a **reconcile**, not a
      one-shot insert (per earlier decision — see Q3 update below), gated by an explicit
      **startup validation step** (today's decision — see Q7 below):
      1. **Validate first, before any DB access:** `ValidateConfiguration(configuration)` reads
         `AdminSeed:Username` / `AdminSeed:Password` and throws `InvalidOperationException` if
         either is missing/empty — message states plainly that the app cannot start without
         them because they provision the only account able to authenticate (once `F0002` locks
         routes down, no admin row means the system is permanently inaccessible, not just
         insecure). Deliberately runs before touching `ONGDbContext` at all: a config problem
         must never present itself as a DB error.
      2. Loads the single admin row, if any: `context.Admins.OrderBy(a => a.CreatedAt).FirstOrDefault()`
         — deliberately `FirstOrDefault`, not `SingleOrDefault`, so a pre-existing data anomaly
         (two rows) fails safe (oldest wins, no crash) rather than throwing at every startup.
      3. **No row exists:** hash the configured password
         (`new PasswordHasher<Admin>().HashPassword(null!, password)`), construct `new Admin(username, hash)`,
         add, save.
      4. **Row exists:** compare against configured desired state and update only what
         changed — `Rename(username)` if `Username` differs (ordinal string compare); rehash
         and `RotatePassword(newHash)` if `PasswordHasher<Admin>.VerifyHashedPassword(admin, admin.PasswordHash, password)`
         is not `Success` (covers both a genuinely different configured password and
         `SuccessRehashNeeded`, .NET's own signal to opportunistically upgrade an old hash).
         Only calls `SaveChanges()` if something actually changed.

      Because `AdminSeeder.Seed` runs synchronously before `app.Run()` (see API layer below) and
      isn't wrapped in a try/catch, an `InvalidOperationException` from step 1 propagates out of
      `Program.cs` and the process exits without ever accepting a request — that unhandled-crash
      behavior *is* the startup validation, not an extra mechanism bolted on afterward. This is
      also what makes CI/CD-driven secret rotation work end-to-end (earlier decision): the
      pipeline's secret store owns the password, and every deploy converges the DB to match it
      — no manual DB edit, no one-time "write it down and hand it to Fernanda" step. Lives
      beside `ONGDbContext` since this is a persistence-layer concern, not a use case.
    - `ONG.Infrastructure.csproj`: add `Microsoft.Extensions.Identity.Core` package reference.
  - **API (`ONG.API`)** — `Program.cs`: after `var app = builder.Build();`, add
    `using (var scope = app.Services.CreateScope()) { AdminSeeder.Seed(scope.ServiceProvider.GetRequiredService<ONGDbContext>(), builder.Configuration); }`
    before `app.Run()`. No controller, no route, no DI registration beyond what the seeder needs
    — this slice exposes zero new HTTP surface, matching the slice objective.
  - **Config** — new `AdminSeed:Username` / `AdminSeed:Password` keys (Q4): set locally via
    `dotnet user-secrets set "AdminSeed:Username" ... --project ONG.API` and
    `dotnet user-secrets set "AdminSeed:Password" ...`; in `docker-compose.yml`'s
    `backend.environment` block via `AdminSeed__Username` / `AdminSeed__Password`, following the
    exact `ConnectionStrings__DefaultConnection` double-underscore convention already in use.
    Never committed in plaintext (mirrors the existing `ConnectionStrings:DefaultConnection`
    handling and `back-end/README.md`'s "nunca commitar credenciais" rule).
  - **Tests (`ONG.Tests`)** — this slice is also the first to wire in a runner: add
    `Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio` (xUnit — the idiomatic default
    for new .NET projects) plus `Microsoft.EntityFrameworkCore.InMemory` (to exercise
    `ONGDbContext`/`AdminSeeder` without a live Postgres container) and `ProjectReference`s to
    `ONG.Domain` and `ONG.Infrastructure`.

- **Migrations:** Two separate migrations, generated and committed as two separate commits
  (not squashed) in this slice's branch:
  1. `FixAnimalAdoptedAtColumn` — closes the pre-existing gap documented in `CLAUDE.md`
     (`Animal.AdoptedAt` has no column yet, so `dotnet ef database update` currently fails
     with "the model has pending changes"). This **must** run first: `dotnet ef migrations add`
     diffs against the *whole* current model, so if it runs after the `Admin` entity is added,
     the `AdoptedAt` column fix and the new `Admin` table get silently bundled into one
     migration — exactly what `CLAUDE.md` says not to do ("needs a real migration ... as its
     own change"). Doing it first, as its own commit/migration file, keeps the two concerns
     separated in history while still unblocking `dotnet ef database update` for this slice's
     own verification step.
  2. `AddAdminTable` — adds the `Admins` table (`Id`, `Username`, `PasswordHash`, `CreatedAt`)
     plus the unique index on `Username`, following the naming/shape pattern of
     `20260816145647_AddAnimalLocation.cs`.
- **Explicit reuse:** `Animal`'s private-setter/single-ctor entity shape (research §3);
  `builder.Configuration.GetConnectionString(...)`-style config access, extended to
  `configuration["AdminSeed:Username"]` (research §3); the `{timestamp}_{PascalCaseName}.cs`
  migration naming pattern (research §3). No repository interface/impl pair is reused or added
  in this slice (see Q5 below) — there is nothing yet to justify one.

- **Resolved open questions:**
  - **Q1 (fields):** Exactly `Id`, `Username`, `PasswordHash`, `CreatedAt` — no `UpdatedAt`/
    `IsActive`. Single admin, no admin-management endpoints, no roles (per PRD non-goals for
    EP05) — extra fields would have no reader or writer in this slice or its sibling `F0001.2`.
  - **Q2 (hashing):** `Microsoft.AspNetCore.Identity.PasswordHasher<Admin>` (package
    `Microsoft.Extensions.Identity.Core`), not BCrypt.Net. See architectural decision above.
  - **Q3 (seed mechanism):** Startup-time check in `AdminSeeder`, invoked from `Program.cs` —
    not `HasData`/`InsertData` in a migration. `PasswordHasher<T>` embeds a random salt per
    call, and the password itself only exists at runtime (configuration), so a
    migration-embedded seed would either hard-code a hash (defeating the point of hashing from
    config) or produce a hash that changes — and thus looks like a pending model change — on
    every `migrations add`.
    **Updated after design review:** given CI/CD deploys with no manual step, a pure
    insert-if-missing seed leaves no way to rotate the admin password without touching the DB
    by hand. `AdminSeeder` is now a **reconcile**: insert if no admin row exists, otherwise
    update `Username`/`PasswordHash` in place whenever they no longer match `AdminSeed:*`
    config. This makes the CI/CD secret store (option 1 from the password-provisioning
    discussion) the single source of truth — rotating the pipeline secret and redeploying is
    enough to rotate the admin's password.
  - **Q4 (config source):** New `AdminSeed:Username` / `AdminSeed:Password` keys, following the
    exact env-var double-underscore convention `ConnectionStrings:DefaultConnection` already
    uses. See Config changes above.
  - **Q5 (repository):** No `IAdminRepository`/`AdminRepository`. This slice has no Handler to
    inject one into — the only consumer is `AdminSeeder`, which is itself infrastructure code
    and can depend on `ONGDbContext` directly (same layer). Introducing a repository pair with
    a single, non-use-case caller would be the premature abstraction `CLAUDE.md` warns against.
    `F0001.2`'s login `Handler` is the first real consumer of an `Admin` lookup by username —
    that slice introduces `IAdminRepository` when there's an actual use case to justify it.
  - **Q6 (unique constraint):** Add `OnModelCreating` with `HasIndex(a => a.Username).IsUnique()`.
    A duplicate admin username is a genuine data-integrity invariant this table must enforce,
    directly part of "create the `Admin` table correctly" rather than scope creep, and it acts
    as a defense-in-depth backstop if `AdminSeeder`'s own idempotency check is ever bypassed.
  - **Q7 (startup credential validation, added post-design):** Once `F0002` protects every
    route behind auth, the seeded `Admin` becomes the *only* way into the system — so a missing
    `AdminSeed:Username`/`AdminSeed:Password` must fail startup outright, not start a system
    nobody can ever log into. This slice already had the guard clause (Q3); today's change makes
    it an explicit, named `ValidateConfiguration` step that runs *before* any `ONGDbContext`
    call, so the failure is unambiguously "you forgot to configure the admin credentials," never
    a downstream DB/connection error. No new mechanism beyond that — `Program.cs` doesn't
    catch the exception, so the unhandled crash on missing config is itself the startup
    validation.

## §4 — Tests BEFORE Implementation (TDD)

> First tests in the repository — `ONG.Tests` gets xUnit + `Microsoft.EntityFrameworkCore.InMemory`
> wired in as part of this slice (see §3). "E2E" here means end-to-end for *this slice's* surface
> (seed mechanism → DB state), since there is no HTTP endpoint yet.

- [ ] *(unit)* `Admin` ctor sets `Username`/`PasswordHash` to the given values, `Id` to a
  non-empty `Guid`, and `CreatedAt` to ~`DateTime.UtcNow`. — maps to DB Impact (parent spec).
- [ ] *(unit)* `Admin.Rename(newUsername)` updates `Username` only; `Admin.RotatePassword(newHash)`
  updates `PasswordHash` only — neither touches `Id`/`CreatedAt`. — maps to the reconcile design
  (today's decision) needing behavior methods, not open setters.
- [ ] *(unit — sad)* `AdminSeeder.ValidateConfiguration` throws `InvalidOperationException` with
  a message identifying which key(s) are missing when `AdminSeed:Username` and/or
  `AdminSeed:Password` are missing/empty, instead of skipping silently or throwing
  `NullReferenceException` — asserted independently of any `ONGDbContext`/`DbSet`, proving the
  check runs before persistence is touched. — maps to "explicit error handling" (CLAUDE.md code
  quality rules), NFR3, and Q7 (the seeded admin is the only way into the system once `F0002`
  ships, so misconfiguration must crash startup, not silently start an inaccessible system).
- [ ] *(integration)* Saving a second `Admin` with a `Username` that already exists throws
  (`DbUpdateException`) — proves the unique index from Q6 is actually enforced by
  `ONGDbContext`. — maps to FR1 ("a single `Admin` user exists").
- [ ] *(integration)* `AdminSeeder.Seed`, given valid `AdminSeed` config and an empty `Admins`
  table, inserts exactly one `Admin` whose `PasswordHash` is **not** the plaintext password and
  verifies successfully via `PasswordHasher<Admin>.VerifyHashedPassword`. — maps to NFR1 (secure,
  non-reversible hashing).
- [ ] *(E2E — happy)* Given valid `AdminSeed:Username`/`AdminSeed:Password` configuration and no
  existing `Admin` row, running the startup seed path once results in exactly one `Admin` row in
  the database matching the configured username, with a verifiable password hash. — maps to FR1.
- [ ] *(E2E — happy)* Given an `Admin` row already exists and `AdminSeed:Password` in config has
  changed since it was created (secret rotation), running the seed path again updates the
  existing row's `PasswordHash` to verify against the *new* password (and no longer against the
  old one) without inserting a second row. — maps to today's CI/CD rotation decision (Q3 update).
- [ ] *(E2E — sad)* Given an `Admin` row already exists and `AdminSeed:Username`/`AdminSeed:Password`
  in config are **unchanged** (simulating a normal redeploy with no rotation), running the seed
  path again inserts **no** additional row and leaves the existing row's `PasswordHash` byte-for-byte
  unchanged (no gratuitous rehash/write). — maps to FR1 + the idempotency risk flagged in
  research §7 (no seeding precedent existed before this slice).

                    "These provision the only account able to authenticate; the application " +
                    "cannot start without them.");

        }
    }
