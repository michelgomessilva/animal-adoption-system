## §1 — Slice Objective

Introduce the `POST /auth/login` endpoint that validates a username/password pair
against the `Admin` identity seeded by `F0001.1` and returns an auth credential on
success, a generic 401 on invalid credentials, and a 400 on missing/malformed input.
This is the second and final slice of `F0001`: it exposes the first HTTP surface for
authentication, using the `Admin` entity, `ONGDbContext.Admins`, and
`Microsoft.AspNetCore.Identity.PasswordHasher<Admin>` that `F0001.1` already landed. It
does not itself protect any other route — that is `F0002`.

## §3 — Design *(filled in Design, ~150–200 lines)*

> Architectural decision and the concrete changes. Resolve all open questions from the
> research notes here. No code — decisions and shapes only.

### Architectural decision

Mirror the existing Command+Handler+Controller pattern exactly (no MediatR, synchronous
`Handle`, `LoginCommand` bound directly as the controller action parameter). Introduce
two new small abstraction pairs, both structurally identical to the one existing
repository pattern:

- `IAdminRepository` / `AdminRepository` — username lookup.
- `ITokenGenerator` / `JwtTokenGenerator` — credential issuance (JWT, HMAC-SHA256
  signed, claims `sub`=Username and `adminId`=Id, expiry from config).

Auth failures (unknown username, wrong password) are communicated by
`LoginHandler.Handle` returning `null` rather than throwing. `AuthController` branches
explicitly on `null` to return a generic 401 ("invalid username or password" — never
reveals which field was wrong, per FR3). This avoids repeating the
`AdoptAnimalHandler` bare-`throw new Exception(...)` gap CLAUDE.md flags, without
introducing global exception-handling middleware for a single endpoint's expected
failure path.

Input validation (FR4 — missing/malformed fields → 400) uses standard `[Required]`
data-annotation attributes on `LoginCommand`, relying on the already-present
`[ApiController]` attribute's automatic model-validation behavior (automatic 400 +
`ProblemDetails` on invalid `ModelState`, and on malformed JSON body) — zero custom
validation code. No prior precedent to match either way (research §5), so the
framework-idiomatic choice wins.

**Alternatives rejected:**
- A generic `Result<T>`/discriminated-union wrapper for Handler outcomes — no
  precedent in the codebase (`CreateAnimalHandler` returns the entity directly), and a
  nullable return fully expresses this Handler's two outcomes without new
  infrastructure.
- Custom exception types + global exception-handling middleware — would also fix the
  real `AdoptAnimalHandler` gap, but that's explicitly out of scope for this slice
  (Q4); would blow the ~400-line diff budget on an unrelated fix.
- Server-side session/opaque token — rejected: NFR2 ("no shared mutable state in the
  credential-verification path") favors a self-contained token; a JWT needs no
  server-side session store and sets up F0002's future Bearer-auth middleware for
  free.

### Changes by layer

- **API (`ONG.API`)** — new `Controllers/AuthController.cs` (`[Route("auth")]`,
  `[HttpPost("login")]`), constructor-injects `LoginHandler` by concrete type (matches
  `AnimalController`'s convention). `Program.cs`: register
  `IAdminRepository→AdminRepository`, `ITokenGenerator→JwtTokenGenerator`,
  `LoginHandler` (all `AddScoped`, same lifetime as existing registrations); call
  `JwtTokenGenerator.ValidateConfiguration(builder.Configuration)` at startup,
  immediately after `AdminSeeder`'s validation — same fail-fast-crash-on-misconfig
  timing/pattern. Add `public partial class Program { }` at the end of `Program.cs` so
  `WebApplicationFactory<Program>` can reference it from `ONG.Tests` (a top-level
  Program.cs's implicit `Program` class is `internal` by default).
- **Application (`ONG.Application`)** — new
  `UseCases/Auth/Login/{LoginCommand,LoginResult,LoginHandler}.cs`; new
  `Repositories/IAdminRepository.cs` (`Admin? GetByUsername(string username)`); new
  `Security/ITokenGenerator.cs` (`string GenerateToken(Admin admin)`).
- **Infrastructure (`ONG.Infrastructure`)** — new `Repositories/AdminRepository.cs`
  (implements `IAdminRepository`, constructor-injects `ONGDbContext`,
  `Admins.FirstOrDefault(a => a.Username == username)` — a real username-filtered
  query, explicitly not `AdminSeeder`'s "grab the first row" shortcut, per research
  §7 risk). New `Security/JwtTokenGenerator.cs` (implements `ITokenGenerator` using
  `System.IdentityModel.Tokens.Jwt`; reads `Jwt:Key`/`Jwt:Issuer`/`Jwt:ExpiryMinutes`
  from `IConfiguration`; static `ValidateConfiguration(IConfiguration)` fail-fast
  check mirroring `AdminSeeder.ValidateConfiguration`). New NuGet dependency:
  `System.IdentityModel.Tokens.Jwt` in `ONG.Infrastructure.csproj` — deliberately
  **not** `Microsoft.AspNetCore.Authentication.JwtBearer`, since this slice only
  issues tokens; validating/consuming them on protected routes is F0002 (Q5).
- **Domain (`ONG.Domain`)** — no changes. Credential verification stays a
  Handler/Infrastructure concern via `PasswordHasher<Admin>`, matching
  `AdminSeeder`'s existing precedent: `new PasswordHasher<Admin>()` instantiated
  directly inside `LoginHandler`, not injected — there is no `IPasswordHasher<Admin>`
  DI precedent anywhere in this codebase to break from.
- **Tests (`ONG.Tests`)** — add `ProjectReference` to `ONG.Application` and
  `ONG.API`; add `Microsoft.AspNetCore.Mvc.Testing` package (per
  `docs/spec-driven-development.md:200-204`, this is the named slice for that). New
  test files per §4.
- **Config** — `appsettings.json` / `appsettings.Development.json` gain a non-secret
  `Jwt:Issuer` and `Jwt:ExpiryMinutes` (e.g. `60`) entry. `Jwt:Key` is a secret — set
  via `dotnet user-secrets` locally and an environment variable in Docker/deploy,
  same handling as `AdminSeed:Password` (NFR3 precedent).

### Migrations

None — the `Admin` table already exists from F0001.1; this slice adds no new
persisted state.

### Explicit reuse

- Command+Handler shape from `CreateAnimalCommand`/`CreateAnimalHandler` (sync
  `Handle`, plain POCO Command, no MediatR).
- Repository interface/implementation split from `IAnimalRepository`/
  `AnimalRepository` (interface in `Application.Repositories`, implementation in
  `Infrastructure.Repositories`, constructor-injects `ONGDbContext`).
- `Microsoft.AspNetCore.Identity.PasswordHasher<Admin>` hash/verify calls, exactly as
  `AdminSeeder.cs:41` already does.
- Controller convention from `AnimalController` (`[ApiController]`, class-level
  `[Route]` with no leading slash, Command bound directly as the action parameter).
- `AdminSeeder.ValidateConfiguration`'s fail-fast-at-startup pattern, reused
  structurally (not literally) for `JwtTokenGenerator.ValidateConfiguration`.

### Resolved open questions

- **Q1 (credential form)** — JWT, HMAC-SHA256 signed, via
  `System.IdentityModel.Tokens.Jwt`. Self-contained (no server-side session store,
  satisfies NFR2), and sets up F0002's Bearer-auth consumption for free. Claims kept
  minimal: `sub` (username), `adminId`.
- **Q2 (repository)** — Yes, add `IAdminRepository`/`AdminRepository`, mirroring the
  only existing repository pattern. `AdminSeeder` keeps its current direct
  `DbContext` access unchanged (out of scope to refactor an already-shipped file).
- **Q3 (error surfacing)** — No exception middleware. `LoginHandler.Handle` returns
  `null` on any auth failure; `AuthController` returns a generic 401. FR4 (bad input)
  is handled entirely by `[ApiController]`'s built-in `ModelState` validation via
  `[Required]` — no custom code.
- **Q4 (AdoptAnimalHandler DI gap)** — Left untouched. Pre-existing, unrelated
  defect; fixing it here would exceed this slice's scope and diff budget.
- **Q5 (auth middleware)** — Not added. This slice only *issues* tokens;
  `AddAuthentication`/`UseAuthentication` and route protection are F0002.
- **Q6 (test infra)** — Yes: add `ONG.Application`/`ONG.API` project references and
  `Microsoft.AspNetCore.Mvc.Testing` to `ONG.Tests.csproj`, plus
  `public partial class Program { }` in `Program.cs`. This is the slice
  `docs/spec-driven-development.md` names for that setup to start.
- **Q7 (validation)** — `[Required]` data annotations on `LoginCommand`, relying on
  `[ApiController]`'s automatic 400 behavior. No guard clauses or custom validation
  code needed.

## §4 — Tests BEFORE Implementation (TDD)

> Explicit test list written **before** any implementation. Must include at least
> **1 happy path** and **1 sad path** end-to-end test.

- [ ] *(unit)* `LoginHandler.Handle_ValidCredentials_ReturnsResultWithToken` — a fake
  `IAdminRepository` returns a seeded `Admin` whose `PasswordHash` was produced by a
  real `PasswordHasher<Admin>`; a fake `ITokenGenerator` returns a known token string;
  asserts `Handle` returns a non-null result carrying that token. Covers FR2.
- [ ] *(unit)* `LoginHandler.Handle_UnknownUsername_ReturnsNull` — fake repository
  returns `null`; asserts `Handle` returns `null` and the token generator is never
  called. Covers FR3.
- [ ] *(unit)* `LoginHandler.Handle_WrongPassword_ReturnsNull` — fake repository
  returns an `Admin` whose hash was produced from a *different* password; asserts
  `Handle` returns `null`. Covers FR3.
- [ ] *(integration)* `AdminRepository.GetByUsername_ExistingUsername_ReturnsMatchingAdmin`
  — `EntityFrameworkCore.InMemory` `ONGDbContext` seeded with one `Admin`; asserts the
  correct entity is returned by username (not "first row in the table" —
  guards against copying `AdminSeeder`'s shortcut, per research §7). Covers FR2.
- [ ] *(integration)* `AdminRepository.GetByUsername_UnknownUsername_ReturnsNull` —
  InMemory DB with no matching username; asserts `null`. Covers FR3.
- [ ] *(E2E — happy)* `Login_ValidCredentials_Returns200WithToken` — via
  `WebApplicationFactory<Program>` with the `DbContext` swapped to InMemory and
  `AdminSeed:*`/`Jwt:*` config supplied in-test; `POST /auth/login` with the correct
  seeded username/password returns 200 and a non-empty token in the response body.
  Covers FR2 + parent Acceptance Criteria happy path.
- [ ] *(E2E — sad)* `Login_WrongPassword_Returns401WithGenericMessage` — same
  factory; correct username + wrong password returns 401 with a message that does
  not reveal which field was wrong. Covers FR3 + parent Acceptance Criteria sad path
  (wrong password).
- [ ] *(E2E — sad)* `Login_MissingPassword_Returns400` — same factory; request body
  missing the `password` field returns 400 with a validation message, no token
  issued. Covers FR4 + parent Acceptance Criteria sad path (missing field).
